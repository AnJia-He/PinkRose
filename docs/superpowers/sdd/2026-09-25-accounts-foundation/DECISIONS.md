### ⚠️ D0b —— **第二个没替你拍的字符问题：`〇`**（请你定，我没定）

**这个换法顺带做了一件事**：把 **`〇`（U+3007）和 `々`（U+3005）从"能注册"变成了"不能注册"**。

**两个字符的情况不一样：**

| | 审查的判断 |
|---|---|
| **`々`（U+3005）** | **拒掉无所谓。** 它是"重复号"（重复前一个字），不是中文人名用字；唯一现实场景是日文汉字姓（佐佐木写作佐々木），而那两个写法本来也不同形 |
| **`〇`（U+3007）** | **「是真的有点代价，不算无所谓」** —— 它不是日语专用字，是**中文正式写法里的零**（`二〇二六年`），中文输入法打得出来、GB 18030 有。而这个字段是**展示用昵称**，`〇〇` 当昵称在中文语境里很自然 |

**关键的一句（审查验过）**：**安全性上收下 `〇` 不花钱** ——
Unicode 规范化不动它、没有和它同形的重复码点，而最像的 `0` 和 `O` 今天本来就放行。

### D3 —— `node:sqlite` 在测试里跑不起来，绕了一层。

这个不是决策，是**踩到坑之后的必然选择**，但你应该知道，因为它改了计划原文。

计划的写法是 `import { DatabaseSync } from 'node:sqlite'`。**这一行在真跑时没问题，
在测试里直接起不来。**

根因（子代理查到源码级）：

> vitest 2 的加载器判定"这是不是内置模块"时，**先剥掉 `node:` 前缀**，
> 再拿裸名 `sqlite` 去比 Node 的内置模块名单 —— 而那份名单里存的偏偏是
> **带前缀**的 `node:sqlite`。于是它认定 `sqlite` 是个不存在的三方包，炸在解析那一步。
>
> 上游修过这个（vitest-dev/vitest#7179），但**只进了 vitest 3**。本仓库是 2.1.9，
> 而 2.1.x 的最后一版就是 2.1.9 —— **升补丁版没用，只有升大版本才有。**

它试过四种 `server.deps.external` 配置写法，**全部无效**（配置层拦不住，因为拿到正则去比的
已经是剥完前缀的 id 了）。

**采用的绕法**：`process.getBuiltinModule('node:sqlite')`。

- 只困在 `server/db.ts` **一个文件**里。外面的人只认 `openDb` 和 `Db`，碰不到 `node:sqlite`
- 类型是准的（Node 自带的类型表里有它，**不需要任何 `as`/`any`**）
- **不碰任何配置**（`vite.config.ts` 改了半天又完全还原了）
- 测试和真跑走**同一条路**（两边都实测过）

**代价**：生产代码里多了一处"因为测试引擎的 bug 而写的东西"。

**中期建议**：把 vitest 升到 3，然后这一处能还原成计划原样。
升级本身是大事（跑测试的引擎换了），不该塞进 Task 1。

## 三、踩到的坑

### 坑 1 —— 计划里一条测试**根本测不到它想测的东西**

计划的 Task 1 有一条测试叫「迁移是幂等的，开两次不炸」，写法是：

```ts
const db = openDb(':memory:'); db.close()
expect(() => { const d = openDb(':memory:'); d.close() }).not.toThrow()
```

**它测了个寂寞。** `:memory:` 每次调用都是**一个全新的空库**，
所以两次走的都是"从 0 开始迁移"那条路 —— 而**幂等要验的是"同一个库开第二次"**。
`:memory:` 恰恰做不到这件事。

子代理按规矩做了变异（把 `i = current` 改成 `i = 0`），**测试全绿**，
然后它做了我认为是这件事里最漂亮的一步：**没有去调断言，而是用一个真文件证明了
那个变异确实是真 bug**：

```
first open: OK
second open THREW -> table users already exists
```

**后果很实**：「迁移在真文件上幂等」是迁移系统的核心承诺，
**后面四个阶段加表（作品表、模型配置表、预设表）全都依赖它** —— 而现在它零覆盖。

**我的裁定**：补一条用真临时文件开两次的测试 ✓ 正在补。
（顺带：这正是这个项目的老规矩"变异没红时先问'是断言抓不住，还是这个变异根本没制造 bug'" ——
这次是**断言抓不住**，而且原因值得记下来。）

### 坑 2 —— `Config` 加一个字段，连带改了 5 个测试文件

计划的文件清单只列了 4 个文件。但 `Config` 一多一个必填字段，

### 坑 3 —— **一个会在第三步炸、而且你救不回来的 bug**（审查抓到并复现了）

这条是今晚最值钱的一个发现。

**问题**：数据库迁移的写法是「执行一句建表 → 记下版本号」。但这两步**各自独立提交**，
中间没有"要么都成、要么都不成"的保证。

**后果**：一条迁移里只要有**两句** SQL，第二句失败 →
**第一句已经永久生效了，可版本号没记上** → 下次启动它以为没跑过、再跑一遍 →
撞上"表已经存在" → **每次启动都炸**。

**而用户（你）没有自救路径** —— 数据库里是半截状态，删了库你的账号就没了，
不删库它永远起不来。

**审查不是纸上推演，它造出了那个状态**：手工做了个"表在、版本号没记上"的库，
连开三次，三次全抛 `table users already exists`，而且版本表里**攒下 3 行**。

**今天为什么没炸**：现在只有**一条**迁移，而且只有一句 SQL —— 触发不了。
**但它一定会在后面炸**：设计文档里排着四段，每段都要往迁移数组里追加一条，
而加作品表、加模型配置表、加预设表，**都很可能是"建表 + 插默认行"或"建带外键的表"** —— 那就是两句。

**我的处理**：修了（把每一步迁移包进事务，失败就整体回滚），并且补了一条测试 ——
**故意造一条会失败的迁移，验它没留下半个状态**。

> **这就是"计划里写的东西不一定对"的又一个例子**：那三行代码是我写的计划里的原文，
> 一路照抄下来，单元测试全绿（因为只有一条迁移），**要等有人真的写出第二条才会现形**。

### 坑 4 —— **计划里的密码参数，在这台机器上一次都跑不起来**

这个更直接：计划里我写的 scrypt 参数是 `N = 32768`、`r = 8`，**没传内存上限**。

**照抄下来，5 条测试挂 4 条**，报的是：

```
RangeError: Invalid scrypt params: memory limit exceeded
```

**差多少？3072 字节。**

OpenSSL 要 `128·r·(N+2) + 128·r·p` = **33557504** 字节，而 Node 的默认上限是 **33554432** 字节。
**就差 3072 字节**（0.009%），参数直接被判非法。

**修法**：显式传一个内存上限（64 MiB）。`N`/`r`/`p` 和输出格式**一个字符没动**。

**实现者还做了一个我认为对的判断**：把那个上限**钉成常量**，而不是按"数据库里存着的 N/r"现算。
理由：万一数据库被改坏，现算就会把上限抬到能把内存吃光 —— 而钉成常量的话，
超纲参数**0 毫秒内抛错、不申请内存**。

**代价**：以后想把 `N` 调更大，得记得把这个上限一起调。已经写进代码注释和提交信息了。

> **这条也值得记**：这是我写计划时"照着一个常见值抄"的结果 —— `N=32768` 看起来很正常，
> 而它恰好**刚好越过**默认上限。差 3072 字节，不跑一次根本发现不了。

### 坑 5 —— **一行没人测的代码，管的是"任意密码都能登进去"**

这是今晚**最该让你知道**的一条。

**事情是这样的**：密码校验里有这么一行：

```ts
if (salt.length === 0 || expected.length === 0) return false
```

**审查把它删掉跑了一遍 —— 5 条测试全绿。**

**而删掉它的后果是：任何人、用任意密码，都能"登录"一条哈希字段是空的记录。**

链条是这样的（审查用三个探针实测过每一环）：

```
密码哈希字段是空的
   ↓
scryptSync(..., keylen = 0, ...)  ← 不报错，返回一个 0 长度的结果
   ↓
"长度不一样就不比" 那道检查      ← 0 !== 0 是假，所以不触发
   ↓
timingSafeEqual(空, 空)          ← 返回 true
   ↓
登录成功
```

它按"删掉之后"的精确逻辑实跑了一遍，随便给个错密码 → **返回 true**。

**为什么测试咬不住**：测试里那四个"坏哈希"输入，**全部死在更前面的一道守卫上**，
**没有一条能走到这一行**。

**审查那句话点得很准**，我照抄：

> 实现者的变异测试只证明了**被删掉的那圈 try/catch 是死代码**，
> **没有问它的替代品是不是活的** —— 而那一行是活的，而且比 try/catch 重要得多。

（背景：那圈 try/catch 是我在计划里写的死代码，我裁定删掉。**替代它的就是这一行。**
实现者验证了"删掉的是死的"，但没验证"留下的是活的"。）

**我的处理**：补一条测试（往坏哈希列表里加一个能走到这一行的），
然后**删掉那行守卫 → 测试必须红** ✓

> **这一条说明的是**：`删掉它测试全绿` 和 `删掉它没出事` 是两件事。
> **测试全绿只说明测试没覆盖它** —— 而没被覆盖的那一行，可能正好是关键的那一行。

### 坑 6 —— **我的计划里，两段自相矛盾**

密码规则里有一条「密码不能和用户名一样」。我的计划里写了这么一条变异来验证它：

> 「把用户名比较改成 `raw === username`（不转小写）→ 这条测试必须红」

**而计划里那段实现的原文，本来就是 `raw === username`。**

**所以那个变异是个空操作** —— 变异体和原型**逐字相同**，改了等于没改。

发现它的子代理还顺着往下查了一层，而那才是真问题：

> **按那个变异的本意（弱化大小写比较），测试照样抓不住。**
> 因为那条测试里两个名字**全是已经小写的字面量** ——
> 所以"改不改都不红"。**这是一个没有任何测试守着的承诺。**

**这是个真问题**，因为用户名**存的就是小写**，而密码比对用的是**用户原始输入** —— 拿苹果比橘子。
（在"调用方恰好传小写"时是对的，但那是**恰好对**，不是**结构上对**。）

**我的处理**：把比较改成大小写不敏感的，并补一条**密码带大写**的测试。
于是它变成了一个真变异 —— 改回去必须红 ✓

### 子代理留给我的一条教训（我认为很值）

> **变异表是手写的，容易写出"变异目标 == 原实现"的空操作。**
> **如果变异表能由机器确认"这一行真的变了"，这类空操作会被挡在开工前。**

这条我记下了。**和坑 3（迁移不原子）、坑 4（密码参数跑不起来）、坑 5（没人测的守卫）
放在一起看，指向同一件事**：

> **我写的计划里的代码，没跑过。**
> 它们看起来都对 —— 单元测试也全绿 —— 但**"看起来对"和"跑过了"是两件事**。
> 这一夜里有四件事是靠**别人真的去跑一遍**才发现的。

### 坑 7 —— **「变异没红」有三种，今晚集齐了**

变异测试的规矩是"改坏代码 → 测试必须红"。**但"没红"的时候，原因有三种，而处理方式完全不同：**

| 哪种 | 意思是 | 该怎么办 |
|---|---|---|
| **① 断言抓不住** | 测试太弱，改坏了它也不管 | **补测试** |
| **② 变异没制造 bug** | 写的变异恰好和原来等价（"等价变异"） | **换一个真的会坏的变异** |
| **③ 变异没被走到** ← **今晚新长的** | 测试跑的路径**根本到不了你改的那一行** | **换一个能走到那行的变异** |

**①和②在计划三（图上点选那次）都遇过**，当时记的是"变异没红也要查，因为可能只是没造出 bug"。

**③ 是今晚第一次见**，而且它的样子很有欺骗性：

> 实现者按裁定把**字符类那条 message** 改成 `'invalid'`，跑测试 —— **全绿**。
>
> 查下来：那条测试用的是 `checkUsername('!')`，而 `'!'` 的**字符数是 1** ——
> 它在**更前面那道"名字至少 2 个字"的检查**就返回了，
> **永远走不到字符类那条 message**。
>
> **也就是说，那个变异在测试看得见的地方，什么也没改。**

**换成它真正走得到的那条 message（长度那条）→ 立刻红，而且正红在被改的那一行。**

**实现者给了它一个准确的归类**：

> **这是「变异没被走到」，不是「断言抓不住」。**

然后它**没有动断言** —— 这一点很关键。如果它把"没红"当成"断言太弱"，
就会去**加强一条本来没问题的断言**，然后报告里写"修好了"。**那是把一个假信号当成真问题修。**

> **所以「变异没红」的正确动作是三步**：先问"我改的那一行，测试真的走得到吗？"，
> 再问"这个变异真的制造了 bug 吗？"，**最后**才问"是不是断言太弱"。
> 顺序反了，就会去修一个不存在的问题。

### 坑 8 —— **「测试全绿」还有第四种解释：测试根本看不见**

（2026-09-25 早上补记。改的就是下面 §5 第 5 条里说的「建议立刻做」那件事。）

`server/db.test.ts` 里 COMMIT 那条用例的注释，原来写着「把 COMMIT 挪回 try 外面，
这条照样绿 —— **SQLite 自己会把事务回滚掉**」。**后半句是错的**（复审实测）：
SQLite **不会**因为 COMMIT 失败就自回滚 —— 事务会留在打开状态，连接一直占着文件。

**那它为什么照样绿？因为这条用例看不见。** 那个连接没提交的建表动作，
对另一个连接本来就不可见 —— 断言读的是**旧快照**。

**我今早自己复验了一遍**（没直接采信复审的话）：把那两行临时换成 `if (false)`，
连跑 8 次 → **8 次全绿**。验完 `git checkout` 还原，工作区回到 0 改动。

**为什么必须改这句注释**：它原样读下来会让人得出「那两行是防御性的、这条测试不是它们的守卫」，
下一个人就可能顺手删掉 —— 而**那是这里唯一的清理**（删了之后，盘满或并发读者那种现场
会留下一个每次启动都炸、用户还救不回来的库）。
代码一个字没动，只改了注释（提交 `699570a`）。

> **加上坑 7 那三种，「把代码改坏了测试还不红」现在有四种：**
> ① 断言太弱 ② 变异是空操作 ③ 变异没被走到
> ④ **走到了，但它拿到的证据是假的**（旧快照 / 被缓存 / 读的是另一个东西）。
> **④ 最阴**：前三种植得查代码和测试，第四种得问「它凭什么看见的」。

### 1. ⚠️ 一个**要我拍**的产品决定：`〇` 能不能当用户名

**背景**：汉字规则从「`一` 到 `龥` 这个范围」换成了 Unicode 的 **`Unified_Ideograph`**（表意文字本体），
而这一换**顺带把 `〇`（U+3007）和 `々`（U+3005）从"能注册"翻成了"不能注册"**，
**而且一条测试都没覆盖这个翻转。**

**最终审查的判断（比我原来的更硬，我认）**：

> **收下 `〇` 在防冒充上是零成本的。**
>
> 我们关掉的那个洞是「**同形不同码点**」（康熙部首 `⼀` 和汉字 `一` 渲染完全一样、U+F900 那批是规范等价重复）。
> 而 **`〇` 在放行集合里没有任何同形伙伴**，Unicode 规范化也不动它 ——
> **这条字符类存在的唯一理由（防两个看起来一样的账号）对 `〇` 不成立**；
> 而最像它的 `0` 和 `O` 本来就放行，**拒 `〇` 换不来任何安全**。
>
> 代价那一侧反而是实打实的：被挡的人看到「只能用中文、字母、数字、下划线和 ·」——
> **等于告诉一个中国人「二〇二六」不是中文**。
>
> `々` 无所谓（它是重复号，不是中文人名用字）。

**你只要二选一**：
- **收下 `〇`** → 一个码点 + 一句"为什么" + 一条测试
- **不收** → 补一条测试把"拒"钉住

（**不管选哪个，测试都要补** —— 现在这一处是顺带的副作用，没人在守。）
