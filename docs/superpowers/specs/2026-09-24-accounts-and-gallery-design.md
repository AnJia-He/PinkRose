# RuiXing 设计文档 — 账号与作品集

- **日期**：2026-09-24
- **状态**：设计定案，待写实施计划
- **一句话**：给这个「用完就没了」的修图工具装上账号 —— 你的图留下来，你这个人也被记住。
- **平台定位（2026-09-24 用户拍板）**：**web 是给电脑用的**，手机那侧交给**小程序**（web 完成之后再规划）。

---

## 1. 为什么做这个

### 1.1 现在缺的是什么

工具本身已经能用了（上传 → 说话 → 改 → 导出）。但它**不记得任何事**：

- 关掉页面，刚才改的东西全没了
- 换台电脑，什么都没了
- 后端不知道"你是谁"，所以没法给任何人做任何承诺

### 1.2 账号是地基，作品集是它长出来的第一样东西

**作品集不是目的，账号才是。** 作品集只是第一个能证明"账号有用"的东西。

以后要做的每一件事 —— 用量、小程序那边的微信登录、甚至万一要收费 —— **全都站在这套账号上**。所以这一版的重点是**把地基打正**，不是把作品集做花。

### 1.3 和产品主线的关系

原 spec（2026-09-21）的成功线是「下载后第一次用，**30 秒内发出朋友圈**」。那条线**本质是手机场景**，所以：

> **成功线归小程序。** web 这边的目标换成「**在电脑上认真修一张图**」—— 屏幕大、看得清、坐得住。

这不代表可以慢慢做。只是**衡量做得好不好的尺子换了**。

### 1.4 ⚠️ 这一版**推翻**了原 spec 的两条

| 原 spec §8.2 写着 | 现在 |
|---|---|
| **用户账号 / 云存储** —— 「第一版不做」 | **就是这一版要做的** |
| **移动 App** —— 「先 Web 验证交互」 | web 是**独立产品**（给电脑），手机归小程序。web 不再是"原型" |

原 spec 的那两行要一并改掉。

## 2. 边界

### 2.1 做

| 模块 | 内容 |
|---|---|
| **账号** | 注册（含邮箱验证）、登录、退出、改密码、注销、忘记密码 |
| **会话** | 30 天免登录（签名 cookie） |
| **作品集** | 保存时自动进、按天分组、看大图、下载、删除、替换 |
| **用户管理** | 账号、使用情况（多少张 / 多大）、改图偏好、外观 |
| **防护** | 用户名唯一、数据隔离、登录按机器限频、每日生成上限、**找回密码永远有出路** |
| **机器** | 数据库（两张主表 + 一张计数器）、图片存储、邮件发送 —— **各抽成一层** |

### 2.2 不做（这一版）

- **收费** —— 用户明确说不收费。但**防滥用上限要做**（见 §6.6）
- **分享给别人看** —— 作品只有自己能看到
- **二次编辑** —— 作品集**只存成品**，不存"改的过程"，点开不能接着改
- **头像 / 昵称** —— 用户名就是唯一身份
- **作品改名 / 打标签 / 分组** —— 只按天自动分组
- **社交登录**（微信 / QQ 扫码）—— 要企业主体
- **多设备会话管理**（"踢掉其他设备"）—— 以后再说

## 3. 界面

### 3.1 一共四个界面

```
① 登录 / 注册        ← 不属于任何导航（登录之前还没有导航）
② 修图              ← 就是现在这个界面，不动
③ 作品
④ 用户管理
```

### 3.2 导航

**桌面左侧竖着一条**（web 只面向电脑，所以不做手机形态）：

```
┌────┬─────────────────────────────┐
│    │                             │
│修图│                             │
│    │      （当前界面的内容）        │
│────│                             │
│作品│                             │
│    │                             │
│    │                             │
│    │                       [👤]  │  ← 右上角：用户管理
└────┴─────────────────────────────┘
```

- **「修图」「作品」两个一级导航**，竖排在左
- **用户管理收在右上角 👤** —— 它一辈子点几次，不配占一个一级位置
- **切导航不丢工作** —— 修到一半跑去看作品，切回来**还在原地**

### 3.3 ① 登录 / 注册

```
打开
 └─ 有会话 → 直接进「修图」
 └─ 没会话 → 登录页 ─┬─ 有账号 → 用户名 + 密码 ─────────────┐
                     ├─ 没账号 → 注册：用户名 + 邮箱 + 密码   │
                     │            ↓                        │
                     │      收验证邮件 → 点链接 ────────────┤
                     └─ 忘记密码 → 输邮箱 → 收重置邮件 → 设新密码
```

### 3.4 ② 修图（= 现在的界面）

```
传照片 → 说话改 → 点「保存」
                      ↓
          ┌───────────┴───────────┐
          ↓                       ↓
   下载到电脑            自动存进「作品」
```

**「替换还是新存」**（用户 2026-09-24 提的）：

```
同一次修图会话（同一张上传的照片）：
        第一次保存      →  直接存，不打扰
        第二次保存起    →  问一句：
                            ┌─────────────────────┐
                            │ 上次那张要替换掉吗？   │
                            │  [替换]   [再存一张]  │
                            └─────────────────────┘
```

> **为什么**：不然同一张照片改 5 遍就是 5 张几乎一样的图，作品集立刻没法看。
> 「再存一张」仍然允许 —— 只是要用户**明确说要**。

### 3.5 ③ 作品

```
9月24日 · 3 张
   [图] [图] [图]
9月22日 · 5 张
   [图] [图] [图] [图] [图]
```

点开一张 → **看大图 / 下载 / 删除**。

**数据是分两步来的**（这也是"名单本 / 图片柜"分开的原因）：

```
① 先问「有哪些」 → 只拿到一串名字和日期 → 摆出骨架（哪天、几张）
② 再一张一张去取图 → 取到一张显示一张
```

> 名单本小，一下子全拿出来；图片大，一张一张拿。
> 所以用户先看到"有几组、每组几张"，**图陆续跳出来**，而不是对着白屏干等。
> 每取一张都要再验一遍"这张是不是你的"（见 §6.1）。

**⚠️ 张数多了要懒加载** —— 5 GB 是 2500 张以上，**一次全摆出来屏幕会卡**。

> 按天分组天然能救：**默认只展开最近几天**，往下滚再取后面的。
> 分组不只是为了好看，**它同时是分页的边界**。

### 3.6 ④ 用户管理

```
你好，哈吉米              ← 用户名
┌────────┐  ┌─────────┐
│  128 张 │  │  342 MB │   ← 使用情况
└────────┘  └─────────┘
改密码 ／ 退出登录 ／ 注销账号
默认导出尺寸 ／ 默认风格    ← 改图偏好
深色 ／ 浅色              ← 外观
```

## 4. 数据

### 4.1 两张主表 + 一张计数器

**`users`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `username` | **UNIQUE**，存小写 |
| `email` | **UNIQUE**，存小写 |
| `password_hash` | scrypt 的哈希 + 盐（见 §6.2） |
| `email_verified` | 邮箱验过没有 |
| `created_at` | 注册时间 |
| `pref_export_size` | 默认导出尺寸（长边像素） |
| `pref_style` | 默认风格 —— 引用**现有那套风格预设**里的一个；空 = 不预设 |
| `pref_theme` | 深色 / 浅色 |

> 三个偏好**只在"开始一张新图"时生效**（省得用户每次重选），**不改已经调好的东西**。

**`works`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `user_id` | 谁改的 —— **每个查询都带上它**，见 §6.1 |
| `stored_name` | 硬盘上的**随机**文件名 |
| `bytes` | 多大 |
| `created_at` | 什么时候存的（**按天分组靠它**） |
| `updated_at` | 替换过就更新 |

**`usage_daily`**（防滥用计数器）

| 字段 | 说明 |
|---|---|
| `user_id` + `day` | 联合主键 |
| `count` | 这天生成了几次 |

> **为什么单独一张表**：作品集只知道"存了几张"，不知道"试了几次"。有人可以不保存一直生成 —— 那也是在花钱。**计数和保存是两件事。**

### 4.2 数据库

**`node:sqlite`**（Node 24 自带，2026-09-24 实测可用、无实验警告）。数据库就是 `data/ruixing.db` 一个文件。

> **为什么不用 SQLAlchemy/Prisma**：这项目到现在只装过 3 个依赖（React 两个 + 一个读照片信息的），后端是手写的。自带的够用，**少一个要更新维护的东西**。
> 换 Postgres 时**只改 `db.ts` 一个文件** —— 所有 SQL 都收在那一层里。

### 4.3 图片存哪

存硬盘：`data/photos/<随机串>.jpg`。数据库**只记文件名**，不存图片本身。

> **为什么不进数据库**：图片塞进数据库会把库撑爆，而且备份、CDN 全都变难。这是所有人的做法。

**文件名必须是随机串，不能是 1、2、3。** 顺序数字的话，别人改一下数字就拿到你的图了。

**存储抽成一层**：本地用硬盘，以后上线换云存储（OSS / S3），**上面那层代码不用动**。

⚠️ `data/` 整个目录进 `.gitignore` —— 里面是用户的照片和数据库。

### 4.4 删东西的三条规矩

| 删什么 | 必须一起做 |
|---|---|
| **删一张作品** | 数据库删记录 **+ 硬盘删文件**。只删一边 = 硬盘慢慢堆满**再也找不回来的垃圾** |
| **替换一张作品** | 写新文件 → 改记录 → **再删旧文件**（顺序不能反：先删旧的，写失败就丢图了） |
| **注销账号** | 作品全删（记录 + 文件）+ 用量记录全删 |

## 5. 接口

```
POST   /api/signup              注册（发验证邮件）
POST   /api/verify-email        点邮件里的链接（激活 + 自动登录）
POST   /api/login               登录
POST   /api/logout              退出
GET    /api/me                  我是谁 + 使用情况（多少张 / 多大 / 今天还能改几次）
POST   /api/forgot-password     申请重置（发邮件）
POST   /api/reset-password      拿邮件里的令牌设新密码
POST   /api/password            改密码（要登录，且要输旧密码）
DELETE /api/account             注销
GET    /api/works               我的作品（按天分组）
POST   /api/works               存一张
PUT    /api/works/:id           替换一张
DELETE /api/works/:id           删一张
GET    /api/works/:id/file      取图
```

> **取图为什么按 `id` 而不是文件名**：按 id 取，鉴权就是自然的（`WHERE id = ? AND user_id = ?`）；按文件名取会把硬盘上的路径暴露到网址里。

**现有三个 AI 接口全部要加登录检查** —— 它们**花真钱**，是最需要保护的三个。

## 6. 安全

### 6.1 隔离：两件事

**① 用户名 / 邮箱唯一 —— 靠数据库的 UNIQUE 约束，不靠代码查**

代码查有个缝：两个人**同时**注册同一个名字，两边都查到"没被占用"，然后就重复了。数据库的唯一约束没有这个缝。

**② 「你是谁」永远从会话里拿，绝不从请求里拿**

这是最重要的一条铁规矩：

> 取作品的请求里**不带**用户 ID。后端自己从那张「小票」里知道你是谁。

要是让前端传 ID，那谁都能把 ID 改一下看到别人的图。**所有 `works` 的查询都必须带上 `user_id`** —— 包括取图、删除、替换。

### 6.2 密码

存的是 **scrypt** 的哈希（Node 自带）+ 每个用户独立的随机盐。

| 规则 | |
|---|---|
| 最短 | **8 位** |
| 最长 | 128 位 |
| 强制大写/数字/符号？ | **不强制** |
| 字符种类 | 中文、空格、符号**都允许** |
| 不能和用户名相同 | ✅ |

> **为什么"不强制复杂字符"**：强制符号会逼出 `Password1!` 这种**更容易猜**的密码。现在公认的做法是**够长就行**。

**比对必须用 `crypto.timingSafeEqual`** —— 普通 `===` 会因为"比到第几位才不一样"泄漏信息。

### 6.3 用户名

| | |
|---|---|
| 长度 | **2–20 个字符** |
| 允许 | 中文、字母、数字、下划线 |
| 不允许 | 空格、符号、emoji |
| 大小写 | **不区分**（`Zhang` 和 `zhang` 算同一个，防冒充）→ 统一存小写 |
| 保留名 | `admin` `root` `system` `administrator` 等不让注册 |

> **为什么最短是 2 而不是 3**：那是英文网站的习惯（`ab` 这种两字母像垃圾号）。但**中文里两个字的名字太常见了** —— 小明、阿宝、李雷。卡 3 个字符的话，「小明」根本注册不了。

### 6.4 邮箱与找回密码

- 注册要填邮箱，**并且要验证**（点邮件里的链接才算激活）
- 忘记密码 → 输邮箱 → 收一封带**一次性令牌**的邮件 → 点进去设新密码
- 令牌**只能用一次**，**1 小时过期**

> **为什么邮箱必须验证**：不验证的话，别人可以拿**你的**邮箱去注册，你就再也用不了自己的邮箱了。

**未验证的账号 24 小时后可以被同一个邮箱重新注册** —— 做法是**把那个没验证过的旧账号整个删掉，再建新的**（它什么都没存过，删掉没有损失）。不然填错邮箱的人就永远卡住了。

⚠️ 只能删**未验证**的账号。验证过的账号占用的邮箱**永远不释放**。

**邮件发送也抽成一层**：
- **本地开发**：不真发 —— 邮件写到 `data/outbox/*.txt`，**链接同时打印在终端里**（这样本地也能完整走通、能测）
- **上线**：换成发信服务的 HTTP 接口（调接口就行，不用装东西）

### 6.5 会话（那张「小票」）

登录成功 → 发一个签名的 cookie：`用户ID.过期时间.签名`，`SESSION_SECRET` 签名。

| 属性 | 挡住什么 |
|---|---|
| **HttpOnly** | JS 读不到 → 页面被塞坏代码也偷不走 |
| **SameSite=Lax** | 别的网站伪造请求带不上这张票（CSRF） |
| **Secure**（上线后） | 明文 http 下不发送 |
| **签名** | 用户改不了票里写的是谁 |
| 有效期 | **30 天** |

⚠️ **`SESSION_SECRET` 放在 `.env` 里**。**没配就拒绝启动** —— 绝不允许用一个写死在代码里的默认值（那等于没有签名）。

### 6.6 防滥用

| 限制 | 值 | 为什么 |
|---|---|---|
| 每天生成次数 | 每人每天 **20 次** | **每次生成都是真钱**，不设上限 = 有人能一夜刷光你的额度 |
| AI 接口速率 | 每账号每分钟 **10 次**（所有 AI 接口一起算） | 挡脚本刷 |
| 登录尝试 | 同一台机器（IP）每分钟 **10 次** | 挡猜密码的脚本。**只限频率，不锁账号** —— 见 §6.7 |
| 作品容量 | 每人 **5 GB**（约 2500–5000 张） | 挡的是"拿你当网盘"的人。**这个数正常用户一辈子碰不到** —— 它的作用不是限制用户，是**兜底** |
| 邮件发送 | 同一邮箱 **1 分钟 1 封** | 不然被人当发信机用 |

**「生成次数」怎么数**：只数 `/api/edit`（真正出图的那一下，一次约 12,900 tokens）。
`/api/route` 和 `/api/suggest` 也花钱但小得多，它们归上面那条「每分钟 10 次」管 —— 数进 20 次里会让用户说三句话就用完了。

**存储上限要"主动说"，不能等用户撞上才知道**：

> 用到 **80%** 就在「使用情况」那里变色 + 一句话提醒他删几张。
> **等用户存不进去了才告诉他"满了"，是最糟的一种做法** —— 他那一刻正想保存，你把他堵在门口。

**另外说清楚这条限制为什么存在**（免得像小气）：它挡的是"拿你当网盘"的人，不是挡正常用户 —— 5 GB 是 2500 张以上。

**真的满了之后（四件事）：**

**① 图照样给你 —— 这是最重要的一条。**

「保存」其实是**两件事**：下载到电脑 + 存进作品集。

> **存档失败了，下载不能跟着失败。**

用户那一刻的目的是"拿到图去发朋友圈"。作品集满了是**我们这边的限制**，不该让他连图都拿不到。

**② 明确告诉他，不含糊。**

> 「空间满了（5 GB）。**这张图已经给你了**，但没能存进作品集。」

只说"存不进去"，他会以为图也没了。

**③ 给一条明路** —— 不是只报错：

```
空间满了。
这张图已经给你了，但没存进作品集。

要替换掉这张吗？   [🖼 缩略图]      ← 显示最旧那张
[ 替换它 ]   [ 我自己去挑 ]
```

**为什么要显示缩略图**：不显示，就变成"我悄悄替你删了一张"；显示了，是**他自己**决定换哪张。

**④ 作品集本身还能用。** 满了只是"不能新增"—— 看、下载、删都不受影响。

> **一条铁规矩：永远不自动删用户的东西。**
> 哪怕满了、哪怕是最旧的、哪怕他一年没登录 —— **他的作品就是他的。**

**登录失败时永远只回一句「用户名或密码不对」** —— 不区分"这个人不存在"和"密码错了"。区分了就等于告诉别人哪些用户名是真的。

> **不收费 ≠ 不设上限。** 用户明确说了不收费，但"每次生成在花钱"这件事没变。上面这几条不是收费，是**别让人把你刷爆**。
> 数字都是**可调的**（配置里的常量），先按这几个值跑。

### 6.7 忘记密码的人，永远有一条出路

**这一节最重要的一条规矩：**

> **重置密码那条路，永远不被登录的频率限制挡住。**
> 它是真用户唯一的出路 —— **把出路也堵上，就等于把人关在门外。**

输错密码的人会依次看到：

| 试到第几次 | 屏幕上出现什么 | 他还能做什么 |
|---|---|---|
| 1–9 次 | 只说「密码不对」 | 接着试 |
| **第 10 次** | 「**密码想不起来了吗？点这里重置**」—— **必须是那一刻屏幕上最扎眼的东西** | **接着试也行**（不拦他） |
| 一分钟超过 10 次 | 「试得太频繁了，歇一分钟」+ **还是那句重置提示** | 等一分钟，**或者点重置** |

**⚠️ 那句提示只是提示，不阻止任何一次尝试。**

> 一旦"错到第 10 次就不让试了"，就变成了**账号锁**。而账号锁有个反作用：
> **别人故意错 10 次，就能把真正的你关在门外。**
> 那不是保护，是**给了别人一个整你的按钮**。

**所以：拦尝试的活儿交给「按机器限频率」，不交给「按账号记仇」。**

**管理员也不例外 —— 不设特殊账号。**

> **为什么不给管理员开一个"不受限制"的账号：**
> ① **特殊待遇会变成路标** —— 有一个账号行为跟别人不一样，攻击者立刻就知道该盯谁
> ② **它给代码开了第二条路** —— 「这个账号就不检查」就是后门；以后每次改登录，都得记得这个例外
> ③ **而且不需要** —— 重置那条路对所有人开着；管理员**自己有服务器**，真进不去就在服务器上改数据库
>
> （对普通用户是耍赖，**对管理员是正解 —— 因为那台服务器就是他的**。）

## 8. 怎么测

沿用这个项目一贯的做法 —— **每个测试都必须有一个能让它变红的变异**。

| 测什么 | 怎么测 | 关键变异（必须能红） |
|---|---|---|
| 密码哈希 / 校验 | 单元测试 | 把 `timingSafeEqual` 换成 `===`；盐改成固定值 |
| 用户名 / 密码 / 邮箱的格式校验 | 单元测试 | 把长度下限从 2 改成 3 → 「小明」那条必须红 |
| **数据隔离** | 接口测试 | **把查询里的 `user_id` 去掉 → 必须红**（这条最重要） |
| 按天分组 | 单元测试 | 跨天边界、空作品集 |
| 会话签名 | 接口测试 | 改一个字节的 cookie → 必须拒；换个密钥签 → 必须拒 |
| **找回密码的出路** | 接口测试 | **在被登录限频的同时，重置那条路必须仍然通** ← 这条最重要 |
| 错 10 次的提示 | 接口测试 | 第 10 次之后响应里必须带「去重置」的提示；**且提示之后仍然接受尝试** |
| 每天生成上限 | 接口测试 | 第 21 次拒 |
| 存储上限 / 快满提醒 | 接口测试 | 超过 5 GB 拒；用到 80% 时响应里必须带提醒 |
| **满了之后图照样给** | 前端 + 接口 | **存档失败时，下载那一半必须照常成功** ← 这条最容易漏 |
| 替换最旧那张 | 接口测试 | 断言旧文件没了、新的在；**且必须是他点了才发生**（不能自动） |
| 删作品 | 接口测试 | **断言硬盘上的文件也没了**（只删记录是经典的漏） |
| 替换作品 | 接口测试 | 断言旧文件没了、新文件在、id 没变 |
| 注销 | 接口测试 | 断言作品记录和文件全清 |
| 邮箱验证 / 重置令牌 | 接口测试 | 令牌用第二次必须拒；过期必须拒 |
| 界面 | 真浏览器检查（现有脚本） | 左侧导航、作品分组、登录页 |
| **作品多了要懒加载** | 真浏览器检查 | 造 500 条 → 首屏**不能一次全渲染**；往下滚才取后面的 |

**接口测试直接测 `createApp()`** —— 现在就是这么做的（`app.test.ts`），沿用。

⚠️ **单元测试和接口测试都碰不到的两类东西**：数据库唯一约束在并发下真的生效吗、cookie 属性真的被浏览器接受吗。这两条要**真浏览器 + 真数据库**验一次，记进验收记录。

## 10. 实施顺序

**这一版很大，分三段走。每段做完都能单独用、单独验收。**

| 段 | 做什么 | 做完之后能用什么 |
|---|---|---|
| **一、地基** | 数据库层 + 用户表 + 注册/登录/会话 + **三个 AI 接口加鉴权** | 能注册、能登录，别人偷不了接口 |
| **二、作品集** | 存储层 + works 接口 + 作品界面 | 保存的图真的留下来了 |
| **三、周边** | 邮箱验证 + 找回密码 + 用户管理四样 + 防滥用上限 | 一个完整的账号系统 |

> **为什么把「三个 AI 接口加鉴权」放在第一段**：那三个接口**花真钱**。在它们有主人之前，后面的东西做得再好都不安全。

## 11. 一句话回顾

**这一版不是加了个相册，是给这个产品装上了「人」。**

以后小程序、用量、任何要"认识你"的东西，全都站在这套账号上。所以它值得做正 —— 该有的隔离、该有的出路、该有的找回，一样都不能因为"本地就我一个人用"而省掉。

> **最后一句，也是这一版真正的分界线**：
> **环境的事可以等**（HTTPS、备案、真短信），**设计的事不能等**（数据怎么隔离、错了怎么提示、谁能花你的钱）。
> 现在按"只有我一个用户"设计，**分享出去那一天就要推倒重做**；按"会有别人"设计，
> **你一个人用的时候一点都不会变麻烦** —— 成本只在设计的时候付一次。
