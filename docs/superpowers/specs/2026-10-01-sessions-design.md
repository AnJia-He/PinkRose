# RuiXing 设计文档 —— **会话**（把"过程"变成一等公民）

2026-10-01 立。

> **这份只讲一件事：让"对话"在服务端有个家。**
> "落地页 → 登录"那条桥是另一份（`2026-10-01-signup-funnel-design.md`）——
> 一个是我们欠的功能，一个是上线的法律前提，节奏不一样，别混在一起改。

---

## 0. 一句话

**上传照片的那一刻就在服务端建一条"会话"，边改边存；关掉浏览器再回来，接着改。**

---

## 1. 为什么现在做

### 1.1 实测：现在**刷新一下就全没了**

2026-10-01 用 Playwright 走的（脚本见 `.superpowers/scratch/`）：

```
上传古镇照 → 画布上有图 ✅ 气泡 1 条 ✅
刷新页面   → 画布上没有图 ❌ 气泡 0 条 ❌ 屏幕上回到「选一张照片」
查服务端   → 服务端存了 13 件作品，但**不知道"对话"这回事**
```

代码上的原因很直白：`src/App.tsx:158` 是 `useState<ChatMessage[]>([])`，
**没有 localStorage、没有 sessionStorage、没有 IndexedDB，服务端也没有对应的表**。
`works` 表只有 `stored_name / thumb_name / bytes / alias / recipe` ——
**它记的是"一张图"，不是"一次对话"。**

后果比"少了历史记录"重：**用户上传了照片、说过话、我们花过一次调用**，
刷新一下全没。照片要重新传，话要重说。

### 1.2 调研：会话历史是**标配**，不是可选项

（2026-10-01 两路调研，证据在 `.superpowers/scratch/NOTES-我们vs豆包-会话历史-2026-10-01.md`）

- **7 家通用对话产品**（ChatGPT / Claude / Gemini / Kimi / 通义 / 元宝 / 清言）：
  **侧栏第一屏 7/7 都是历史会话列表**，单条可删 7/7。
- **没有一家为了隐私放弃"历史"这个概念。** 连 Meta 那种"服务器零日志"的，
  也只是把"不存"做成一个**开关**。行业事实标准：
  **对你的历史不可见，但服务器为安全留 24 小时~30 天**
  （Gemini 72h / Perplexity 24h / OpenAI 与 Claude 30 天）。
- **修图产品那条线**（Lightroom / Canva / 即梦 / Midjourney / Google 相册）：
  **历史的价值一半在图、一半在"它怎么来的"。**
  Lightroom 的调整是"指令栈"，关掉软件再回来还在；Canva 能回滚 1000 个版本；
  Midjourney 把 prompt 写进下载的 PNG。
  ⚠️ **最像我们的反面教材**是 Google 相册那个对话式修图「Help me edit」——
  **它连对话都不存**，但它把"怎么改的"写进了图片文件本身（C2PA 凭据）。

### 1.3 ⭐ 我们缺的其实**只有一样东西**，而它是结构性的

把管理动作跟豆包逐条对完，结论有点出乎意料：

| 能力 | 豆包挂在**会话**上 | 我们挂在**作品（成图）**上 |
|---|---|---|
| 改名 | ✅ | ✅ 详情页 |
| 删除 | ✅ | ✅ 详情页 |
| 导出 | ✅ | ✅ 「下载到我的电脑」 |
| 多端同步 | ✅ | ✅ 存服务端（比它更彻底） |
| 落到一个"库" | ✅ 我的创作 | ✅ 作品库（按天分组） |
| 搜 | ✅ 标题 + **正文** | ⚠️ 只搜作品名 / 日期 |
| **列表本身** | ✅ 会话列表 | ❌ **没有** |
| **过程** | ✅ 完整对话 | ❌ 只留 8 个数字 + 几条原话（配方） |
| **没做完的活儿** | ✅ 草稿分区 | ❌ **刷新即灰飞烟灭** |

**我们对外的一级导航是「修图 / 作品」—— 作品是结果，对话是过程，
而"过程"在我们这儿一个家都没有。**

## 2. ⚠️ 这份文档**推翻一条既有决定**（不静默）

`docs/superpowers/specs/2026-09-24-accounts-and-gallery-design.md` **§2.2** 那一栏写着：

> **二次编辑** —— 作品集**只存成品**，点开**不能接着改**。
> （⚠️ 2026-09-24 改精确：**"不存过程"指的是不存中间图和对话历史**……
> 配方很小，而且**不能用来接着改**，所以本意没破。）

**那条决定当时在管什么**：它在管**作品集**这个库 —— 怕它变成一锅粥
（改了 5 遍就是 5 张几乎一样的图），也怕存储失控。**那个判断在它的范围内是对的**，
这份文档**不动作品集**。

**为什么现在要改**：因为它把两件事混成了一件。

- 「**作品集不存中间图**」—— 仍然成立。作品是用户**挑出来的成品**。
- 「**不存对话历史**」—— 这个结论是**从上一句顺推出来的**，而它没有独立论证过。
  实测下来它有两个代价：**① 刷新即全丢；② 点开旧作品不能接着改**
  （而图我们本来就存着——缺的只有对话）。

**还有一条当时的文档不可能知道的**：落地页上写着

> **「每一步都退得回去」**

那是**对用户做出的承诺**。今天它在一次会话内成立（图在内存里），
**关掉浏览器就不成立了**。

→ **本设计把 §2.2 那一栏改精确**（那一栏要跟着改，不是悄悄绕过）：

| 那条现在应该长这样 | |
|---|---|
| 作品集**只存成品** | 不变 |
| 作品集里**不存中间图** | 不变 |
| ~~不存对话历史~~ → **会话存对话历史；作品不存** | **改** |
| ~~点开不能接着改~~ → **点开那次会话能接着改；作品本身仍然只是一张成图** | **改** |

## 3. 会话是什么

**一次会话 = 一张上传的照片。** 这不是新发明的定义 ——
`accounts-and-gallery-design.md` §3.4 自己就是这么说的：
「**同一次修图会话（同一张上传的照片）**」。
本设计只是**把这个已经存在的概念落成一个有 id 的东西**。

三条性质：

1. **它从"上传那一刻"就存在** —— 不是等保存。没保存的会话叫**进行中**，
   它照样在服务端的列表里（豆包也是这么做的：侧栏有一个「草稿」分区）。
2. **会话之间互不串。** 每次上传 = 新的一条。上下文、素材、消息都不共享。
   ⚠️ 豆包验证过这个模型，而且我们本来就该这样：一张照片上的编辑对另一张没有意义。
3. **「保存」的语义一个字不变** —— 它仍然是"把**现在这一张**导出成一件作品，
   存进作品库"。会话是过程，作品是产物，**两层，不合并**。

## 4. 数据

### 4.1 一张新表

按 `server/db.ts` 的契约**追加**一条迁移（只许往后加、不许改老的）：

```sql
CREATE TABLE sessions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    title       TEXT,              -- 自动取第一条用户消息；可改；null = 还没起名
    original    TEXT NOT NULL,     -- 上传的原图（data/photos 里的文件名）
    base        TEXT NOT NULL,     -- "现在这一张"（每一步覆盖，只留当前）
    thumb       TEXT,              -- 列表上那张小图（和作品的 thumb_name 同款）
    messages    TEXT NOT NULL,     -- JSON：对话
    steps       TEXT NOT NULL      -- JSON：每一步（见 4.3）
);
CREATE INDEX sessions_user_updated ON sessions(user_id, updated_at DESC);
```

**`messages` 的形状**（小，纯文本）：

```ts
type SessionMessage = {
  id: number
  role: 'user' | 'assistant'
  text: string
  at: number
  stepId?: number   // 助手那条挂在哪一步上 —— 「回到这一步」靠它
}
```

### 4.2 文件住在哪

**不新开目录。** 复用 `server/storage.ts` 那一层（`data/photos/`），
它已经能存、能读、能删，**而且只有它碰这个目录**（换云存储时改一处就够）。

⚠️ 两个名字要记住：`original` 是**上传的那张**，永不覆盖；
`base` 是**现在这一张**，每一步换一次。

### 4.3 ⚠️ 存哪几步 —— 这条是这份文档里最要拿准的

**决定：每一步的图都存下来。**

理由只有一条，但够硬：**落地页上写着「每一步都退得回去」。**
不存中间图，那句话在重开之后就变成假的 —— 而这个项目最不能忍的就是
**用户看得见的假话**。

**成本**（实测过的数）：`data/photos/` 现存 1130 个文件共 17.7 MB，
最大一张 0.73 MB；而**会话里进来的图**长边 ≤ 2048 —— ⚠️ 这一条**不是流水线给的**：
`shared/size.ts` 的 `MAX_DIMENSION` 管的是**送给模型的载荷**，画布本身按图的大小开、
只按设备探到的 WebGL 上限缩过（可以远大于 2048）。会话这份 ≤2048 是**客户端在上传时
压出来的**（建会话的原图、每一步的底图，编码前都 `fitWithin` 到 2048 —— 见
`src/core/thumbnail.ts` 的 `bitmapToDataUrl`）。所以**一步一张，量级在 1 MB 以内**。

**两处省钱的细节**：

1. **参数步不产生新图。** 拖滑块走的是本地 WebGL，`base` 那张**位图没变**
   （`pushSnapshot` 里 `base` 是同一个对象）。所以这类步骤**只记参数，
   不存文件** —— `steps` 里若干条指向**同一个文件名**。
2. **`steps[i].image` 就是那一步的 `base`。** 不另存一份"中间图"。

> ⚠️ **2026-10-01 实测更正第 1 条的前提**（写计划时踩到的，代码里写着它是**有意**的）：
> **这个客户端里"参数步"根本不存在。** `src/App.tsx` 有一句既有裁定：
> 「**改 params 从来不 push 快照 —— 快照是给"生成式编辑"用的（裁定 ⑤）**」
> （见 `WorkDetailPage` 那个 `onApply` 的注释）。拖滑块 / 套预设 / 按重置
> 只 `setParams`，**`history` 一动不动**。
>
> 所以：`reusesPrev` 这一版**实际永远是 `false`** —— 保留它是因为 Task 2 有测试、
> Task 5 的恢复要读它，删掉是纯粹的无谓改动；但它省下的那次下载这一版省不到。
> 真正的后果是**必须补一条路**：参数不能跟着 `history` 走，得单独送
> （`SessionPatch.params` → 服务端写到最后一步上），否则验收线第 1 条的
> 「参数全在」在**用户拖完滑块刷新**这个最常见的动作上就是假的。
> ⚠️ 将来真要做"参数也算一步"（能做参数级撤销），那时第 1 条才重新成立 ——
> 而那是**改客户端的撤销模型**，不是改这里。

```ts
type SessionStep = {
  id: number
  label: string           // 「生成式编辑」/「调色」
  image: string           // data/photos 里的文件名（可能和上一步相同）
  params: Adjustments     // 那一步结束时的八个数字
  prompt?: string         // 记着当初那句话（「再来一版」靠它）
  at: number
}
```

### 4.4 ⚠️ 删会话**不删作品**

作品是**独立的一份拷贝**（`works.stored_name` 指向自己的文件）。
用户点「保存」拿走的那张图，**不该因为他回头删了会话就消失**。

这条要写成测试（见 §9）—— "删了会话，作品还在"是**现在最容易写错、且错了没人发现**的一处。

### 4.5 回收与配额

- **保留期**：**到用户自己删为止**（和豆包官方口径一致：「你未撤回、删除或未注销账号期间，我们会保留」）。
- **每用户 5 GB 那条**（§6.6）**这一版仍然不做**，但会话会让存储真正开始增长 ——
  **它和"防滥用那张表"要一起排进下一段**（见 §10）。
- 删账号 = `ON DELETE CASCADE` 把会话一起带走（文件由删除流程一并清）。

## 5. 接口

贴着现有写法（`server/app.ts` 是精确匹配 + **锚定整串**的正则；
依赖整个 `deps` 传下去；GET/DELETE **不读请求体**）。

| 接口 | 干什么 |
|---|---|
| `POST /api/sessions` | 上传时建一条。body `{ image, thumb? }`（原图，base64，和 `WorkInput.image` 同一个形状）→ `{ id }` |
| `GET /api/sessions` | 列表（元数据，**不含图**）。按 `updated_at` 倒序 |
| `GET /api/sessions/:id` | 一条的详情：`title` / `messages` / `steps` / 三个文件名 |
| `PUT /api/sessions/:id` | 更新，**每个字段都可选、谁传更新谁**：`{ base?, thumb?, messages?, steps?, title? }`。⚠️ `base` 传的是**新那张图的字节** —— 只在**底图真的换了**的时候传（生成式编辑之后）；拖滑块那种更新只传 `messages` + `steps` + `title`，**不传图** |
| `DELETE /api/sessions/:id` | 删。**连带删它自己的文件，但不动任何作品** |

原图和每一步的图**不走上面这些** —— 走 `<img src>`，让浏览器自己取
（和作品那两个 `fileUrl` / `fullUrl` 同一个路数）：

| 接口 | 干什么 |
|---|---|
| `GET /api/sessions/:id/file/original` | 原图（全尺寸） |
| `GET /api/sessions/:id/file/base` | 现在这一张（全尺寸） |
| `GET /api/sessions/:id/file/step/:stepId` | 某一步的全尺寸（**跳回去时才取**） |

⚠️ **不做"每一步的服务端缩略图"。** 客户端本来就会给每一步生成缩略图
（`src/core/thumbnail.ts`），**恢复的时候现生成**就行 —— 多存一份，
就是多一份会跟原图对不上的东西。

⚠️ 三条都要 `requireUser` + **`user_id` 比对**（和作品那几条一样：
别人的 id 一律 **404 不是 403**，而且**数据一个字节都不动**）。

## 6. 界面

### 6.1 左栏多一个入口

现在是「**修图 / 作品**」，变成「**修图 / 对话 / 作品**」。

- **修图** = 现在这一次（会话）
- **对话** = 历史会话列表 ← **新**
- **作品** = 我存下来的图 ← **一个字不改**

⚠️ 为什么不是把「作品」改成会话列表：**它们是两个东西**（§3 第 3 条）。
豆包也是两层 —— 会话列表**加上**「我的创作」。

### 6.2 打开就接着上次那条

挂载时 `GET /api/sessions`，取**`updated_at` 最新的那一条**恢复：

- 原图 + 每一步的图 → 解码回 bitmap（和现在内存里的形状一样）
- `messages` / `steps` / `params` → 原样装回去
- **「回到这一步」照常能用**（这就是 §4.3 要存每一步的原因）

没有会话 → 现在那个「选一张照片」的欢迎页（不变）。

⚠️ **恢复出来的会话要标出来**：屏幕上得有一句"这是上次没做完的"，
不能让它看起来像刚传的 —— 否则用户会以为照片是刚上传的。

### 6.3 列表

按天分组（**复用作品页那套 `dayKey` / `dayLabel`，别新写一套**）。
每条一行：**最后那张的缩略图 + 标题 + 时间**。

- 标题：自动取**第一条用户消息**的前若干字；没有消息就用照片原名（去扩展名）
- 悬停/长按出两个动作：**改名**、**删掉**（⚠️ 删要就地确认，走 `.notice` 那套，不弹系统框）

### 6.4 新建

**上传一张新照片 = 自动开一条新会话**（现在的行为本来就是"换图就清空"，只是现在清了就没了）。
顶栏再给一个明确的「新的一张」，免得用户不知道自己在哪条会话里。

### 6.5 现在"不丢"的东西，一条都不能丢

`App.tsx` 里现在有一条已经做到的保证：**切导航不丢工作**（切到「作品」再切回来还在）。
会话落库之后这条仍然成立，而且升级成 **"关掉浏览器也不丢"**。

## 7. 只在这一版做的取舍（写下来免得以后当 bug 修）

- **恢复会话 = 把所有步骤的全尺寸图都取回来。** 一条 5 步的会话大约几 MB。
  变长之后的优化（只取最后 K 步全尺寸、更早的只给缩略图、
  跳回去时再取）**这一版不做** —— 先把"不丢"做对，再说省流量。
- **没有置顶 / 归档 / 项目分组 / 批量删除 / 搜索。** 见 §8。

## 8. 不做什么（这一版）

| 不做 | 为什么 |
|---|---|
| **分享对话** | ⚠️ 豆包的分享是**免登录的公开网页**，且**分享前没有任何提醒**（南都 2025-12-19 实测 8 款国产 AI，只有 DeepSeek 会提醒）。**我们的用户传的是自己的脸。** 要做就先学 DeepSeek 弹一句"拿到链接的人都能看到" —— 那是另一件事 |
| **置顶 / 归档 / 项目分组 / 批量删除 / 管理页** | 豆包有是因为它上千条；我们几十条时这些是负担 |
| **会话内搜索** | 作品页已经有"搜名字或日期"；会话先按时间找。要做得先想清搜标题还是搜正文 |
| **多设备会话管理**（"踢掉其他设备"） | §2.2 本来就排着不做 |
| **一个会话里多张照片** | 会话的定义就是**一张照片**（§3），换照片 = 新会话 |

## 9. 怎么验

**验收线（用户看得见的那条）**：
1. 上传 → 说一句话 → **刷新** → **照片、对话、参数全在**，接着能改
2. 关掉浏览器、重开、进 `/app` → 还是那一条
3. 换一张照片 → **新的一条**，两条互不影响（在 A 里说的话不出现在 B）
4. 「回到这一步」在**恢复之后**仍然能跳回去
5. 删掉会话 → **它存过的作品还在作品库里**
6. **现有 568 件作品一条不动**（迁移只加表，不碰老数据）

**测试要盯住的三处**（这三处错了不会报错，只会静静地错）：
- **跨用户**：拿别人的会话 id → 404，且**两张表的整表快照前后完全相同**
  （照抄作品那几条的写法，alter 掉 `user_id` 时测试必须变红）
- **删会话不删作品**（§4.4）
- **恢复之后不串**：两条会话来回切，`messages` / `steps` 不能互相污染

**照旧要跑**：`npx vitest run`、两个 `tsc`、`check:layout`、`check:dev-urls`。
（`check:layout` 要补「对话」这一屏，否则新页面**没有任何版面检查**。）
