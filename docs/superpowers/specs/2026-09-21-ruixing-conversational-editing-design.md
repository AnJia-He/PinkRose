# RuiXing 设计文档 — 对话式户外修图

- **日期**：2026-09-21
- **状态**：设计定案，待写实施计划
- **一句话**：用户上传一张照片，说人话，照片就变好看了。

---

## 1. 定位

### 1.1 用户是谁

**旅游打卡党。** 用手机拍照、要发朋友圈/小红书的人。

不是摄影师，不是修图爱好者。她不认识"曲线""色阶""HSL"，也不打算学。

### 1.2 她的痛点是"快"，不是"精"

判断这个产品成败的，只有一条线：

> **下载后第一次用，能不能在 30 秒内发出朋友圈。**

做不到这条，她就回去用醒图了。产品做得再精确也没用。

### 1.3 差异化

市面上的竞品（醒图、美图、Lightroom 移动版）都建立在**「滑块」**这个交互范式上：给你一堆参数，让你自己拖。

**我们赌的是另一个范式：用户说人话，AI 翻译成操作。**

- 她说"天太灰了" → 不需要知道"去灰"要调对比度还是清晰度
- 她说"像富士胶片那种感觉" → 不需要会调 HSL 曲线

而且这恰好是大模型真正不可替代的能力：**看懂画面 + 听懂人话 + 决定怎么改**。

### 1.4 明确不做什么

- **不做"滤镜更多"**——滤镜是可以被抄的，理解力不行
- **不做专业调色面板**——曲线、色彩分级、局部蒙版，目标用户根本不会用
- **不做社区**——太重，且偏离核心
- **不做相机联动**（第一版）——见 §8.2

## 2. 核心用户体验

### 2.1 主流程

```
上传照片
   ↓
进入对话，图下方几张小卡片：「天空更蓝」「去掉路人」「日系色调」
   ↓
她说一句话，或者点一张卡片
   ↓
┌─────────────────────────────────────┐
│ 调色部分 → 立刻生效（本地，毫秒级）    │
│ 生成部分 → 后台跑（云端，约 10 秒）    │
│            角落提示「正在去掉路人…」   │
└─────────────────────────────────────┘
   ↓
满意 → 存相册 / 分享
不满意 → 再说一句，或点「微调」拖滑块
```

### 2.2 六个已定案的交互决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| **上传后第一眼** | 直接进对话，配建议卡片 | 卡片门槛低；且用户不开口就不烧钱 |
| **一句话说多件事** | 「一次做完」/「一步步来」由用户选，默认一次做完 | 用户要快；但保留慢的权力 |
| **等 10 秒怎么办** | 调色秒出，生成后台跑 | 把等待拆成「0 秒看到大部分」+「剩一点慢慢补」 |
| **怎么指位置** | 说话为主；模型拿不准时提供点选兜底 | 不打断说话节奏 |
| **八滑块放哪** | 默认藏起来，点「微调」展开 | 常驻会让界面变成 Lightroom，冲淡对话感 |
| **输出多大** | 调色 = 原图尺寸；生成式编辑 = 2048 | 调色不丢画质；生成式受 API 限制，发社交够用 |

### 2.3 建议卡片必须是动态的

**不要写死「天空更蓝 / 去掉路人 / 日系色调」这三张。**

上传后先让模型（VLM）看一眼照片，再生成卡片：

> 阴天海边照 → 「天空救回来」「提亮人脸」「日系通透感」
> 夜市人像 → 「压一下噪点」「暖调氛围」「去掉后面的人」
> 雪山逆光 → 「提亮脸部」「还原蓝天」「增强层次」

用户一看就知道**它真看懂了我的照片**。这是"大模型原生"该有的样子，也是最便宜的信任建立方式。

（代价：每次上传多一次 VLM 调用。但它便宜——不存在图片生成那一万三的 token。）

### 2.4 撤销 = 翻聊天记录

不设「撤销」按钮。**对话记录里每一句话下面挂一张那一步的缩略图，点哪句就回到哪句。**

这样撤销和对比原图是同一个东西，而且符合聊天的直觉。同时满足「一次做完」模式下用户想单独反悔某一件事的需求。

### 2.5 对比原图

**按住图 = 看原图，松手回来。** 跟 Instagram、美图一致，不要发明新交互。

## 3. 技术架构

### 3.1 总体结构

```
┌──────────────────────────────────────────────────┐
│  浏览器（前端）                                    │
│                                                   │
│   对话面板 │ 画布 + 点选标记 │ 八滑块（折叠）        │
│       └──────────┬──────────┘                     │
│            ┌─────┴──────┐                         │
│            │  编辑状态机 │ ← 唯一真相源             │
│            └─────┬──────┘                         │
│            ┌─────┴──────┐                         │
│            │ WebGL 渲染  │ 毫秒级实时预览           │
│            └────────────┘                         │
└───────────────────┬──────────────────────────────┘
                    │ HTTP
┌───────────────────┴──────────────────────────────┐
│  后端（Node）                                     │
│   · 持有 API Key（绝不能进前端）                   │
│   · 意图路由（调 VLM + LLM）                       │
│   · 转发 /images/edits                            │
│   · 请求队列 + 退避重试（账户有 RPM 限制）          │
└──────────────────────────────────────────────────┘
```

**必须有后端。** API Key 一旦进前端，任何人按 F12 就能拿走烧钱。这是硬性要求。

### 3.2 分层：三层 + 意图路由

```
用户："天太灰了，人再亮点，把后面那个人去掉"
                    │
        ┌───────────┴───────────┐
        │   LLM 意图路由         │  看照片 + 懂人话 + 决定走哪条路
        └───────────┬───────────┘
                    │
      ┌─────────────┴─────────────┐
      ↓                           ↓
┌─────────────┐           ┌──────────────┐
│  参数路      │           │  生成路       │
│ 去灰/提亮/   │           │ 去人/换天     │
│ 色温/风格    │           │              │
│ 本地 WebGL   │           │ SenseNova    │
│ 毫秒 免费 可逆│           │ 约10秒 花钱   │
└──────┬──────┘           └──────┬───────┘
       └───────────┬─────────────┘
                   ↓
           合成 → 参数面板实时生效
```

### 3.3 为什么参数层必须是主力（实测数据）

**这不是架构偏好，是被实验逼出来的结论。**

在真人脸照片上实测：

| 指令类型 | 脸部像素改动 | 结果 |
|---|---|---|
| **全局性**（提亮 / 加暖 / 加对比） | **58.6%** | 皮肤毛孔全被抹平，出来是 AI 美颜脸 |
| **局部性**（换背景 + 明确列出保留项） | 13.3% | 脸保住，背景自然替换 |
| **局部性**（磨皮 + 明确列出保留项） | 2.6% | 几乎原样 |

**规律：全局性形容词会让模型把整张图（含人脸）重新想象一遍；局部性指令 + 明确列出「要保留什么」它会老实。**

而"调色"天然是全局操作。

**结论：调色一律走本地参数层。** 除了保脸，还因为：

- **成本**：一次生成约 1.3 万 tokens（图片占 8288）。用户随口一句"再亮一点"都送生成，账算不过来。
- **延迟**：生成 9~11 秒，本地渲染毫秒级。
- **可逆**：参数可无限微调、随时归零；生成出的是新像素，不可微调。

### 3.4 核心数据模型

```ts
type EditState = {
  base: ImageSource        // 当前像素。初始 = 原图（全分辨率）；
                           // 做过一次生成式编辑后，替换成 2048 的生成结果
  params: Adjustments      // 八个滑块
  history: Snapshot[]      // 每句话一个快照，可回到任意一步
}

type Adjustments = {       // 全部归一化到 [-100, 100]
  exposure: number
  contrast: number
  highlights: number
  shadows: number
  saturation: number
  temperature: number
  clarity: number
  vignette: number
}
```

**整个模型只有一条铁律，但它是产品体验的基石：**

> **参数永远不烘焙进 `base`。参数只作用在最终渲染的那一刻。**

三个直接好处：

1. 拖滑块 → 毫秒级、免费、无限次、随时归零
2. 说"去掉那个人" → 只换 `base`，`params` 原封不动继续生效
3. 显示永远是 `render(base, params)`，**同一个函数、同一条路径**，不会出现"某些调整叠加了两次"

### 3.5 一个容易踩的坑：送去生成的图不带参数

用户已经调暖了（色温 -30），然后说"把后面那个人去掉"。送哪张图给模型？

- ❌ **送调过暖的图** → 模型返回的图已经含了那 -30，回来再被 `params` 作用一次 → 变成 -60，**颜色炸了**
- ✅ **送原图** → 干净，参数只作用一次

**选送原图。** 用户当前的参数值作为**文本上下文**告诉 LLM（"用户已把色温调到偏冷"），让它在写 prompt 时补偿。对"去路人"这类结构性任务，这点色彩差异几乎无影响，换来的是完全不会双重叠加的干净模型。

**确定性比聪明重要。**

## 4. 模型接入（商汤 SenseNova）

### 4.1 端点与模型

| 用途 | 模型 | 端点 |
|---|---|---|
| 图像编辑（手） | `sensenova-u1.5-fast` | `POST /v1/images/edits` |
| 看图 + 意图路由（眼睛+大脑） | `kimi-k3` | `POST /v1/chat/completions` |

Base URL：`https://token.sensenova.cn/v1`

> 注：官方 `SenseNova-Skills` 客户端里硬性写着"编辑只能用 `sensenova-u1.5-lite`"。**这个限制是错的**，服务端接受 `u1.5-fast`，已实测。

### 4.2 请求格式

```json
{
  "model": "sensenova-u1.5-fast",
  "images": [{ "image_url": "data:image/jpeg;base64,..." }],
  "prompt": "...",
  "n": 1,
  "size": "1024x768",
  "watermark": false,
  "prompt_extend": true,
  "response_format": "b64_json"
}
```

**`response_format` 必须用 `b64_json`。** 用 `url` 会把图放在 `aoss.cn-sh-01.sensecoreapi-oss.cn` 上，**那个域名经常连接超时或 DNS 解析失败**——生成明明成功了却拿不到图（开发中栽过两次）。`b64_json` 直接内联返回，取 `data[0].b64_json`。

### 4.3 硬性约束（全部踩过）

| 约束 | 内容 | 违反的后果 |
|---|---|---|
| **尺寸格式** | 只接受 `auto` 或 `WIDTHxHEIGHT` | 传 `"1K"`/`"2K"` 直接 400 |
| **32 倍数** | 宽高必须是 32 的倍数 | 1200 会被拒 |
| **尺寸范围** | `[512, 4096]` | — |
| **宽高比** | ≤ 3:1 | — |
| **必须锁尺寸** | **绝不能用 `auto`** | 见下 |

**「必须锁尺寸」是最重要的一条。** 实测：同一张图、同一句 prompt：

- `size="auto"` → 输出 2368×1792，**地平线从 78% 漂到 65%，构图变了**
- `size="1024x768"`（=原图尺寸）→ 输出 1024×768，**地平线 80%，连跑三次完全一致**

**`auto` 是在「重画」，锁定尺寸才是「编辑」。** 这是这个产品能不能做的分水岭。

所以：上传后先把图**缩放并对齐到 32 的倍数**，再把这个尺寸显式传进去。

### 4.4 尺寸策略

**两条路分开管。谁干的活谁负责。**

**调色 → 本地做，不经过模型 → 用原图尺寸，一个像素不丢。**

调色是 WebGL 在本地算的，跟送不送模型无关，所以完全可以在原图全分辨率上跑。用户绝大多数操作是调色，所以大多数时候她拿到的是完整画质。

**生成式编辑（去人 / 换天）→ 2048。**

原因：模型是"照着你给的图重画一张"，不是"在原图上改几个点"。API 最大只到 4096 且宽高必须是 32 的倍数，图越大 token 越贵（1024×768 已占 8288 个图片 token）。所以先缩到**长边 2048**、再把宽高各自对齐到 32 的倍数，然后送上去；它画回来的也就是 2048。

代价：**用了去人/换天的照片，分辨率降到 2048。** 发朋友圈/小红书完全够（微信自己还会再压一次）。

**为什么不让生成结果也保住原图尺寸**（原 v2 方案，**现降级为待验证，不要当成稳的**）：模型即使锁定尺寸，构图仍有 1~2% 的轻微漂移（实测地平线会动），直接把改动区域贴回原图会**错位**。要做必须先解决对齐问题（例如特征点微调对齐）。

### 4.5 Prompt 写法规范（关键）

实测结论：**prompt 的写法直接决定人脸保真度。**

**必须遵守两条：**

1. **只描述「改什么」，不要用全局形容词。**
   - ❌ `Brighten the photo, add a warm tone, increase contrast`（全局 → 重画整张脸，58.6% 改动）
   - ✅ `Remove the person standing behind the subject`（局部 → 脸只动 13.3%）

2. **永远显式列出「要保留什么」。**
   ```
   Preserve the person's identity, facial features, eyes, eyebrows,
   hair, and skin texture exactly as they are.
   ```
   加上这一句，同样的磨皮任务脸部改动从 58.6% 降到 2.6%。

**模板：**

```
{只描述要改的那一处}
Keep everything else exactly as it is, especially {明确点出不能动的东西}.
Preserve the person's identity, facial features, eyes, eyebrows, hair, and skin texture.
```

**待验证**：`prompt_extend=true` 会让服务端改写我们的 prompt。我们自己的 prompt 已经写得比较细了，服务端改写是帮忙还是添乱，**需要做一次 A/B 实测**。第一版先保持 `true`。

### 4.6 多图输入（"我想要这种效果"）

API 支持一次传多张图，官方文档明确说明（"多图任务中，请按预期顺序提供图像，并说明每张图像的作用"）。实测色彩迁移非常精确：底图平均色 `(149,154,154)` + 参考图 `(84,73,66)` → 输出 `(87,79,70)`，几乎完全等于参考图，且构图不动。

**但「色调参考」这个功能不走生成层，走参数层。**

| 用户说 | 走哪条 | 理由 |
|---|---|---|
| "我想要这种**色调**" | **参数层** | 分析参考图的色彩分布 → 换算成八滑块数值 → 本地应用。免费、毫秒、可拖、不毁脸 |
| "我想要这种**氛围**" | **生成层** | 逆光感、胶片颗粒、特定光影结构——调色表达不了 |

色调迁移用标准算法（如 Reinhard color transfer，或提取 3D LUT）实现。

> **未决**：`usage.images_count` 始终报 `1`，即使传了两张图。计费口径不明，涉及多图功能上线前必须查清。

### 4.7 错误处理

| 失败场景 | 处理 |
|---|---|
| **429 限流** | 账户有 RPM 上限（实测被打过）。后端**串行队列 + 指数退避**，绝不并发轰炸 |
| **网络超时** | `token.sensenova.cn` 连接很不稳定，必须重试（3~5 次，递增等待） |
| **图下载失败** | 用 `b64_json` 从根上避免 |
| **生成失败** | **调色参数一个都不丢**，提示"再试一次"，静默重试 |
| **结果尺寸不符** | 统一 resize 到目标尺寸 |
| **LLM 路由失败** | 降级：原文当 prompt 直接走生成，不要给用户看报错 |

**铁律：任何失败都不能让用户丢掉已经调好的参数。** 那是她最在意的东西。

### 4.8 成本

一次生成式编辑约 **12,900 tokens**（输入 8,835，其中图片占 8,288；输出 4,144）。

**这决定了产品形态**：调色零成本、生成按次收费。免费额度策略见 §7.2。

## 5. 本地调色引擎

### 5.1 八个参数

全部归一化到 `[-100, 100]`：

| 参数 | 作用 |
|---|---|
| `exposure` | 整体亮度 |
| `contrast` | 对比度 |
| `highlights` | 高光 |
| `shadows` | 阴影 |
| `saturation` | 饱和度 |
| `temperature` | 色温 |
| `clarity` | 清晰度/中间调微对比 |
| `vignette` | 暗角 |

**外加一键风格预设**（日系、胶片、通透、黄昏……）——预设的本质就是一组 `Adjustments` 的预设值，不需要单独引擎。

### 5.2 渲染管线

**WebGL2 片段着色器，八个参数一次算完，一次 draw call。**

```
原图纹理 → [单次 fragment shader: 8 参数] → 画布
```

不要串八个 pass（慢且累积精度损失）。所有参数在一个 shader 里按顺序计算。

拖滑块时只更新 uniform，不重新上传纹理 → 60fps 顺滑。

### 5.3 色彩管理（必须做）

**这是修图产品的经典翻车点：**

- iPhone 拍的照片默认是 **Display P3 色域 + HEIC 格式**
- 如果转码时不做色彩管理：送上去是 P3、回来是 sRGB，**颜色会明显偏**（红色发暗、绿色发艳）
- 用户会觉得"修完比原图还难看"

**规范：内部统一用 sRGB。** 解码时做 P3 → sRGB 转换，送模型前保证是 sRGB。HEIC 需要解码支持（浏览器 `createImageBitmap` 在新版本已支持 HEIC，否则用 wasm 解码器兜底）。

### 5.4 EXIF

导出时**保留拍摄时间、GPS 等 EXIF 信息**。旅游照的时间和地点对用户有意义，别丢。

## 6. 意图路由

### 6.1 输入输出

后端把 **照片 + 用户的话 + 当前参数状态** 一起给 LLM，要它回结构化 JSON：

```json
{
  "route": "params" | "generate" | "both",
  "param_deltas": { "temperature": -20, "shadows": 15 },
  "edit_prompt": "Remove the person standing behind the subject. Preserve the person's identity, facial features, eyes, eyebrows, hair, and skin texture exactly as they are.",
  "reply": "天有点灰，我提了下通透度；后面那个人也帮你清掉了。",
  "needs_disambiguation": false
}
```

### 6.2 输出「增量」而不是「绝对值」

用户说"再暖一点"，**让模型输出 `+20` 而不是 `-40`。**

理由：输出绝对值的话，模型得先看当前色温是 -20、再算出 -40。**让 LLM 做算术是经典翻车点**，它会算错、会算飘。

输出增量则把累加和边界钳制（clamp 到 `[-100,100]`）交给确定性代码。LLM 只负责它擅长的事：**听懂"再暖一点"大概是要多少**。

### 6.3 歧义处理

照片里人多的时候（"把后面那个人去掉"——后面三个人，哪个？），LLM 返回 `needs_disambiguation: true`，前端提示：

> **你在图上点一下要改的地方？**

用户点一下 → 在该点画出标记 → 连同标记一起送模型。

（实测：在图上画标记让模型只改标记处是可行的，红圈本身也会被正确擦除。）

### 6.4 建议卡片生成

上传后单独调一次 VLM，让它看完照片输出 3 张卡片：

```
你看这张照片，判断用户最可能想改什么。返回 3 条，每条一句话，12 字以内，
是用户会说的话（第一人称口语），不要专业术语。
```

## 7. 未决问题与风险

### 7.1 色彩管理（高优先级）

见 §5.3。**必须做，不做必翻车。** 但 HEIC 解码在浏览器端的支持度需要实测。

### 7.2 成本与免费额度（未定）

一次生成 1.3 万 tokens，**白送烧不起**。第一版需要定：

- 每天免费几次生成式编辑？（调色不限）
- 超出后怎么办：付费 / 看广告 / 排队到次日

**第一版建议**：不做付费系统，但**后端强制串行 + 限流保护**，UI 上显示每次生成的状态。额度策略等有真实用户数据后再定。

### 7.3 本地调色引擎好不好看（最大风险）

**参数层是主力，它调出来好不好看直接决定产品下限。**

如果自研的八滑块调出来一股"廉价滤镜味"，整个产品就废了——因为用户看到的大部分结果都来自它。

**必须在写代码早期就用真实照片验证。** 这是整个项目最该先做原型验证的部分。

### 7.4 真实相机素材从未测过

此前所有测试用的都是程序生成的合成图 + 网图，**从未测过真实相机照片**。

已记入待办：拿到相机（索尼 M5，型号待确认）后拍五类照片各测一轮——逆光人像、背景路人、天空过曝、夜景、大图链路。放 `test-photos/`（已在 `.gitignore` 排除）。

还需确认：**收不收 RAW。** RAW 是完全另一条色彩链路，第一版建议明确不收。

### 7.5 生成结果不可复现

同一句 prompt 连打三次，天空蓝色分别是 `(12,133,248)`、`(0,163,236)`、`(1,151,237)`——**结果不稳定**。

用户不满意点重试会得到不一样的图。交互上需要兜住：**保留历史版本，让她能在几个结果之间挑**，而不是只能一遍遍重试。

## 8. MVP 范围

### 8.1 做什么

| 模块 | 内容 |
|---|---|
| **前端** | 上传 → 对话 → 画布预览 → 滑块（折叠）→ 导出 |
| **参数层** | WebGL2 八参数渲染 + 一键风格预设 |
| **生成层** | `/images/edits` 接入，去人 / 换背景 |
| **意图路由** | kimi-k3 看图 + 分类 + 输出增量 |
| **建议卡片** | 上传后动态生成 3 张 |
| **点选兜底** | 图上点一下 = 画标记，处理多人歧义 |
| **历史** | 每句话一个缩略图，点了回到那一步 |
| **对比原图** | 按住看原图 |
| **导出** | 存相册 + 系统分享面板 |

**技术栈建议**（可改）：Vite + React + TypeScript；WebGL2 手写 fragment shader；后端 Node + Fastify，内存队列。

### 8.2 不做什么（第一版）

- **相机联动**——浏览器做不了（各厂协议需原生 SDK），是另一个大工程
- **用户账号 / 云存储**
- **批量处理**
- **付费系统**
- **移动 App**——先 Web 验证交互
- **涂抹圈选**——只做「点一下」，圈选留到后面
- **RAW 支持**
- **局部重绘贴回原图保尺寸**——留作待验证（有对齐风险），第一版生成式编辑的输出就是 2048

## 9. 验证方式

### 9.1 纯函数优先

系统的确定性核心是两个纯函数，**必须单元测试**：

- `render(base, params) → pixels`：给定输入像素和参数，断言输出像素
- `route(userText, currentParams, image) → Decision`：mock 掉 LLM，断言路由决策

AI 的不确定性被关在这两个函数的边界之外，其余全是确定性的。

### 9.2 端到端场景

用真实旅游照跑这几条：

1. "天太灰了" → 只动参数，不调 API（**零成本断言**）
2. "把后面那个人去掉" → 走生成，脸区改动 < 20%
3. "我想要这种色调" + 参考图 → 走参数层，色调迁移成功，脸零改动
4. 生成中拔网线 → 参数不丢，提示重试
5. 连发三句话 → 串行执行，不并发

### 9.3 体验验收线

**30 秒内发出第一条朋友圈。** 从打开到分享，用秒表掐。
