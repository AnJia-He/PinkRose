# PinkRose 审美创作 Agent 设计

2026-11-02 立。

## 一句话

让 PinkRose 像一位有审美判断、会动手、能接住情绪、也能给出方向的摄影搭子：
先看懂照片和用户真正想要什么，再从可扩展的内置能力库中选择最合适的做法，
经过确定性复核后执行。所有内部调度都留在产品内部，用户只感知到一次自然、可信、
能落到画面上的协作。

## 1. 目标与边界

### 1.1 要解决的问题

当前链路已经能完成单次调色、生成式编辑、会话记忆和外部资料搜索，但各项能力仍主要
围绕“这一句话调什么参数”工作。它缺少一层稳定的审美判断，因而容易出现：

- 把用户想要的氛围直接理解成一串滑杆，结果技术正确但画面没有主次；
- 局部能解决的调整被误派给图片生成，或者同一个效果本地、云端各做一次；
- 普通修图很利落，但用户问“怎么修”“没有灵感”时只能给泛泛建议；
- 能力越多，模型越容易在不了解工具边界时自行拼装；
- 回复有礼貌，却缺少对画面和用户处境的真实回应。

本设计增加一个内部“创作导演”层，把身份、审美判断、能力选择、工具执行和结果复核
串成一条稳定链路。它不是另一个聊天产品，也不把内部工作流表演给用户看。

### 1.2 产品边界

- 本地调色、人像、几何、镜头、预设和 Lut 仍然优先，免费、快速、可回退。
- 生成式编辑只在结构性变化确实需要时调用，一次用户输入最多生成一版。
- 照片、会话历史和长期偏好不会因为审美判断或搜索被额外外发。
- 用户最新明确指令高于历史偏好；用户说“就轻微一点”时，不擅自加码。
- 不假装能读出人物关系、人生经历或心理状态，只依据画面证据表达。
- 不承诺“看不出来”“完美”“不会被发现”，只说明改了什么、保留了什么。
- 用户界面不出现 Agent、Skill、MCP、Plugin、上下文压缩、检索失败等内部词。
- 本设计只覆盖桌面体验和现有服务链路；手机布局不改。

## 2. 用户感知

用户不需要知道后面有几个模块，只会感受到四种稳定体验：

1. **直接指令**：说“脸亮一点、背景别抢”，画面马上有对应且克制的调整，回复只说明
   做了哪一处、保住了什么。
2. **开放咨询**：说“不知道该怎么修”，先指出画面里真实成立的优点和一个主要问题，
   再给两条方向不同但都可执行的思路，最后推荐风险较低的一条。
3. **情绪时刻**：说“拍得好丑”时，不空喊“不丑”，也不读心；只如实指出画面里成立
   的地方，再把下一步缩小到一件看得见、能撤回的事。
4. **复杂修改**：说“做出电影感，但不换背景”，先拆成色彩、明暗、质感和保留项；
   能本地完成的先本地完成，确需结构性变化时才生成，并且只生成一次。

回复长度按任务变化：直接修改通常 1 至 2 句；审美咨询最多 3 至 4 句；闲聊自然简短。
身份稳定，措辞不固定，不用固定安慰句或客服式开场。

## 3. 总体架构

```text
用户输入 + 当前照片
  -> 输入与隐私守卫
  -> 上下文组装
       - 固定身份
       - 单会话审美轨迹
       - 跨会话稳定偏好
       - 当前参数、预设、Lut、回退位置
       - 可用能力清单
  -> 审美导演（一次模型调用）
       - 看懂画面与意图
       - 选择审美方向
       - 组织可执行计划
  -> 外部事实检查（仅确实需要时）
       - 内置搜索 MCP
       - 最多一次搜索
       - 必要时一次最终整理
  -> 计划编译与审美复核（确定性）
       - 能力白名单
       - 参数钳制与去重
       - 修改幅度、保留项、事实与回复检查
  -> 执行
       - 本地参数 / 人像 / 几何 / 镜头 / 预设 / Lut
       - 最多一次图片生成
       - 正常摄影搭子回复
```

普通修图仍然只需要一次对话模型调用；只有确实依赖照片之外的事实时才走搜索链路。
审美复核不调用第二个模型，也不把“正在分析”“正在协调能力”等步骤显示给用户。

## 4. 核心模块

### 4.1 身份内核

身份继续由 `server/replyGuide.ts` 持有，不在每轮重新人格扮演。它规定的是判断姿态，
不是固定台词：

- 像一个懂摄影、会看图、共同做决定的人；
- 先说画面证据，再说判断，再给动作；
- 有立场，但不把个人喜好当成唯一答案；
- 尊重用户的审美意图，同时敢于指出会破坏画面的做法；
- 不讨好、不卖惨、不制造依赖，不把照片好坏等同于人的价值；
- 不猜测用户的人生、关系、性格或情绪。

### 4.2 审美 Skill

审美 Skill 是版本化的判断规则，不是所有风格模板。每次请求始终先经过同一套主判断，
再按照片类型和用户意图附加对应子规则。

主判断顺序：

1. **任务和场景**：这是人像、旅行、街拍、夜景、产品、食物、建筑、旧照修复，还是
   仅仅想要一个社交平台版本？
2. **照片自己在说什么**：主体、视线、光线、色彩、空间、动作和情绪各自在哪里。
3. **技术底子**：曝光、白平衡、裁切、噪声、清晰度、透视和边缘是否有明确问题。
4. **视觉主次**：第一眼应该落在哪里，第二层是什么，哪些元素在抢视线。
5. **色彩与光线关系**：肤色是否自然，高光是否有层次，冷暖是否服务氛围，背景是否
   和主体相互打架。
6. **真实性边界**：人物身份、五官、皮肤质感、产品标签、建筑结构和原始故事中哪些
   不能被改掉。
7. **做什么最值**：优先选择一项能提升画面关系的关键动作，再用不超过三项轻量动作
   补齐，而不是把所有滑杆都推一遍。
8. **何时停手**：出现皮肤塑料感、颜色断层、背景过亮、主体被压暗、风格压过内容等
   迹象时立即收手。

各场景子规则只增加必要重点，不改变主判断：

- **人像**：先看人物状态和视线，再看肤色、皮肤纹理、轮廓和背景分离；默认保留身份、
  骨相和真实质感。
- **旅行 / 风景**：先看空间层次和主景，再看天空、地平线、透视和色彩；不把立体场景
  压成均匀的高饱和明信片。
- **街拍 / 夜景**：先保护灯光和现场气，再看黑位、色偏和噪点；不通过全局提亮抹掉
  夜晚。
- **产品 / 食物**：先看材质、边缘、高光和色彩准确，再清理背景；不改变商品结构、
  标签和食物真实颜色。
- **建筑 / 室内**：先看直线、透视和空间明暗，再处理窗光与冷暖；不为了“震撼”扭曲
  结构。
- **旧照修复**：先区分自然老化和需要修补的损伤；生成只用于无法由本地修复完成的部分，
  并始终保留人物身份和时代质感。
- **社交发布**：先看缩略图可读性、画幅和主体占比，再决定裁切与色彩；不把平台流行
  风格凌驾于照片本身。

Skill 的详细内容以声明式规则保存，由注册表按场景装配。新增一个场景只增加规则、触发
条件和验收样例，不修改主路由代码。

### 4.3 能力注册表

模型不能直接调用任意函数、地址或提示词。它只能从本轮能力清单里选择已注册的能力。
每项能力都有版本、输入输出、可用条件、费用、隐私级别、是否可回退和单轮次数限制。

```ts
type CapabilityKind =
  | 'local'
  | 'generation'
  | 'knowledge'
  | 'provider'
  | 'workflow'

type CapabilityDescriptor = {
  id: string
  version: number
  kind: CapabilityKind
  description: string
  input: 'param-deltas' | 'recipe' | 'preset' | 'lut' | 'edit-prompt' | 'query'
  cost: 'free' | 'model' | 'remote'
  privacy: 'local' | 'image-to-cloud' | 'public-query'
  undoable: boolean
  maxPerTurn: number
}
```

初版注册这些能力：

| 能力 | 类型 | 作用 | 默认限制 |
| --- | --- | --- | --- |
| `local.tone_color` | local | 曝光、对比、高光、阴影、白平衡、色彩、去雾、HDR 等可靠滑杆 | 一轮可合并，禁止重复描述 |
| `local.portrait` | local | 磨皮、美白、红润、点修等已有本地人像能力 | 默认保留皮肤纹理和身份 |
| `local.geometry` | local | 透视、镜头畸变、水平 / 垂直校正 | 只在画面有明显几何问题时 |
| `local.lens_focus` | local | 径向虚化、移轴、焦点位置 | 不替代结构性背景替换 |
| `local.style_recipe` | local | 由受控配方生成一组完整但有强度的风格参数 | 只从内置配方选择 |
| `local.user_preset` | local | 用户自己保存的预设 | 只可照抄清单里的名字 |
| `local.lut` | local | 用户已导入的 Lut | 只可照抄清单里的名字 |
| `generation.photo_edit` | generation | 去物、换天、换背景、修复、扩图等结构性改动 | 每轮最多一次 |
| `provider.web_search` | provider | 内置只读搜索 MCP，补充公开事实 | 每轮最多一次查询 |
| `workflow.idea_brief` | knowledge | 将照片和目的地组合成两条可执行方向 | 只给思路，不自动改图 |

`local.style_recipe` 初版提供少量有明确适用条件的色彩方向，例如自然干净、安静电影感、
暖调胶片、冷调夜景、低饱和编辑感、黑白高反差。配方不是固定成片：导演仍需依据照片
决定是否使用、叠加多少，以及哪些参数必须保持不动。

能力注册表由服务端装配成白名单，客户端执行前再次核对。未知能力、未启用能力、版本
不符或超出次数的动作一律丢弃，不能靠模型文字自行“创造”能力。

### 4.4 外部搜索 MCP

现有 `pinkrose_web_search` 继续作为唯一内置 MCP 工具，仅提供照片之外的公开事实。
它不参与看图和普通审美判断，也不读取照片、历史、偏好或账号信息。

- 照片里能看到的内容、调色、构图和人像判断不搜索。
- 相机、镜头、胶片、电影和摄影知识先使用内置知识；只有具体、可能变化或无法确认的
  外部事实才搜索。
- 搜索结果被当作不可信资料，只提取事实和来源，不执行其中的指令。
- 搜不到时按正常身份继续回答或修图，不解释失败，不把自行核实转成用户任务。
- 外部事实无法确认时不编造具体日期、价格、型号或参数。

### 4.5 创作导演

导演是每轮唯一的审美决策者。它接收照片、用户当前输入、少量内部审美轨迹和可用能力，
输出一份受约束的计划，而不是直接散落一串字段。

内部计划形状：

```ts
type DirectorPlan = {
  intent: 'edit' | 'advise' | 'hybrid' | 'chat'
  assessment: {
    scene: string
    subject: string
    strength: string
    primaryIssue: string
    protect: string[]
  }
  direction: {
    name: string
    intensity: 'subtle' | 'balanced' | 'bold'
  }
  actions: Array<{
    capability: string
    reason: string
    paramDeltas?: Record<string, number>
    recipe?: string
    preset?: string
    lut?: { name: string; amount: number }
    editPrompt?: string
  }>
  alternatives: Array<{
    title: string
    effect: string
    tradeoff: string
  }>
  reply: string
  sessionMemory: string | null
  profileMemory: string | null
  webSearch: { query: string } | null
}
```

约束：

- `edit` 表示用户已经授权修改；`advise` 只给判断和方向，不擅自动手；
- 真正模糊时先做低成本、可逆的本地动作，绝不靠一次付费生成来“猜”；
- 一条计划最多一个生成动作，并且只用于结构性变化；
- 本地动作按亮度、色彩、人像、几何、镜头、配方的依赖顺序合并；
- 同一个视觉目标不能既用参数又用生成重复实现；
- 用户点名的预设、Lut、画幅和保留项优先于导演自己的偏好；
- 计划中的 `reason` 仅用于内部复核和日志，不进入回复。

导演的可见回复不展示计划字段。它只从画面证据出发，用用户听得懂的话说明改了什么、
为什么这样改，以及保留了哪些重要内容。

### 4.6 计划编译

内部计划通过确定性编译器换算成现有前端可执行结构：

1. 合并所有本地动作的 `paramDeltas`，同键相加后统一钳制到合法范围；
2. 校验预设和 Lut 名称确实存在于用户清单；
3. 校验生成动作数量、尺寸和保留项；
4. 生成动作存在时，路由为 `generate` 或 `both`，否则为 `params`；
5. 无动作的咨询仍走 `params`、增量全零，不伪造一次付费生成；
6. 编译结果继续使用现有 `RouteDecision` 和 `applyDecision`，避免建立第二套执行器；
7. 内部 `assessment`、`direction`、`reason` 和计划编号不进入公开 API 或聊天记录。

### 4.7 审美复核

复核器不负责“再想一次审美”，只负责拦住确定会破坏结果的情况。两项独立检查：

**计划一致性**

- 能力是否存在、已启用、版本匹配、次数和输入形状合法；
- `advise` 计划不得携带生成动作；
- 生成必须有具体、单目标、带保留项的英文编辑指令；
- 用户点名的预设和 Lut 不被悄悄替换；
- 本地和生成不得表达同一件事；
- 事实型回答必须有可核实来源或明确停止给出具体信息。

**画面风险**

- 默认强度下，磨皮、饱和度、清晰度、HDR、柔光、暗角和锐化不能叠成塑料感；
- 用户明确说“轻一点”时，所有动作按同一强度收口；
- 人物场景必须保留身份、五官、表情、发型、皮肤纹理和自然边缘；
- 背景替换必须保留主体、构图、机位、透视和光照方向；
- 夜景、产品、食物和建筑要检查最容易失真的局部，而不是只看整体观感；
- 人像塑形、换装、换发等身份相关动作不因一张普通照片自动触发；
- 生成式计划不得使用“完美”“看不出”“保证一致”等承诺。

复核通过后执行。复核只是将动作降幅、去掉重复项或移除危险生成，不另起模型重写整份
计划。任何被拦截的原因只记录能力编号、风险类别和时间，不记录照片、回复原文或历史。

### 4.8 回复守卫

公开回复在发送前做最后一层确定性检查：

- 不出现内部实现词、搜索失败说明、压缩提示、置信度、参数名堆砌或能力编号；
- 不把核实、补资料或重新描述需求变成用户义务；
- 不出现空泛夸奖、读心、外貌羞辱、关系暗示和固定客服开场；
- 不承诺生成模型无法保证的“完全一致”或“不会有人发现”；
- 来源链接可以保留，正文仍先说结论，不变成资料列表；
- 用户明确问内部实现时，只解释产品能做什么，不展开后端结构。

触发守卫时优先保留已经可执行的本地动作；需要改回复时，由当前意图和画面证据生成一句
自然的正常回复，不套统一安抚句。

### 4.9 记忆与审美轨迹

复用现有单会话和跨会话记忆，不另建第三套状态。

单会话内部摘要新增这些审美轨迹：

- 当前已经确认的视觉方向；
- 已经做过且用户认可或不认可的动作；
- 用户明确要求保留的主体、色彩、构图和质感；
- 下一步还没有解决的问题。

跨会话仍只保存稳定偏好，例如“自然肤色、低调对比、少磨皮、优先 4:5”。最新明确指令
优先于旧偏好。单次情绪、照片内容、人物身份、关系和地点不进入长期偏好。

阈值、最近原文数量、隐藏存储和失败回退继续遵循现有记忆设计。用户可见回复不出现
“记忆”“摘要”“压缩”等词。

## 5. 执行优先级

每轮按以下顺序决定是否停止：

1. 先用现有照片和会话判断，不拿搜索替代看图；
2. 能用本地、可逆动作解决时，不调用生成；
3. 用户点名预设、Lut 或当前画幅时，优先尊重用户选择；
4. 视觉方向明确但需要整组色彩语言时，可选择一条受控配方；
5. 只有结构、内容或现实中不存在的画面变化才使用生成；
6. 需要照片之外的最新事实时才调用搜索 MCP；
7. 任何一步都没有足够依据时，先给可执行方向或停在安全调整，不盲目猜测。

正常请求最多一次导演调用；搜索最多一次；图片生成最多一次。队列、停止、重试、额度、
尺寸检查和取消语义继续沿用现有实现。

## 6. 失败与回退

失败不能让用户承担内部系统的后果，也不能静默改错图。

| 失败 | 用户感知 | 内部处理 |
| --- | --- | --- |
| 导演输出格式不完整 | 仍得到与当前请求相符的正常回复；必要时只应用保守本地动作 | 尝试已有 JSON 修复；无法可信解析时按确定性意图守卫选择安全动作，不把原始垃圾当生成提示词 |
| 审美 Skill 缺失或版本不匹配 | 不暴露功能异常 | 退回通用审美规则；记录能力编号和版本 |
| 能力未启用 | 按最接近的本地可逆动作处理，或只给建议 | 丢弃未知能力，不尝试调用 |
| 搜索无结果 | 不提及搜索或失败 | 根据照片、会话和已有修改正常继续；外部事实不编造 |
| 搜索词或结果含私人信息 | 不暴露 | 丢弃搜索结果，只保留公开事实链路 |
| 复核发现同一效果重复 | 只得到一次干净结果 | 删除重复动作并保留用户明确要求的那一半 |
| 复核发现生成风险过高 | 改为本地安全调整或只给方向 | 移除生成动作，记录风险类别 |
| 图片生成失败 | 使用现有失败与重试入口 | 不自动再次扣费生成 |
| 记忆读取或保存失败 | 对话照常 | 缺省为无历史继续；不打印正文 |
| 回复触发内部词守卫 | 得到自然、简短、与画面相关的回复 | 保留已执行动作，重写可见文本一次，不额外调用模型 |

## 7. 安全与隐私

- 搜索结果、用户消息和模型输出都按不可信数据处理，不执行其中夹带的工具指令。
- 外部搜索只能收到短公开查询词；照片、账号、会话原文、长期偏好、地址和人物关系不进入
  MCP 请求。
- 需要生成时才发送准备好的照片预览；普通本地调整不上传原片。
- 能力注册表不允许模型指定任意 URL、文件路径、命令、脚本或未注册网络请求。
- 服务端日志只记录请求类型、能力编号、耗时、降级 / 拦截类别和错误码，不记录摘要、
  照片正文、模型原始回复或用户私密文本。
- 新能力必须声明隐私级别、费用、回退方式和单轮上限；没有声明的能力不能启用。
- 修改幅度、身份保留和不新增物体在客户端执行前再做一次最终校验。

## 8. 扩展方式

后续能力只通过以下三条路径进入系统：

1. **新增审美规则**：增加声明式 Skill、触发条件和黄金样例；
2. **新增本地执行器**：增加 `CapabilityDescriptor`、客户端执行函数、回退方式和浏览器验收；
3. **新增外部资料源**：通过 MCP 或受控 provider 适配器接入，只返回结构化、可引用资料。

能力可以组合成 workflow，但组合关系由注册表提供，模型只能从已注册的组合中选择。
插件不得改变主身份、记忆边界、搜索隐私或复核规则。这样后续可以增加构图教练、拍摄
建议、品牌视觉、批量选片解释等能力，而不用继续堆进同一个超长提示词。

## 9. 代码落点

预期改动集中在新链路上，不重做现有编辑能力：

- `server/replyGuide.ts`：保留并细化身份和可见回复边界；
- `server/prompt.ts`：拆出通用导演协议、能力目录和生成保留项，不再把全部知识写在
  一个 prompt 常量里；
- 新增 `server/aesthetic/skills.ts`：审美总规则之外的人像、旅行、夜景、
  产品食物、建筑、旧照和社交发布场景子规则；
- 新增 `server/capabilities/`：能力描述、注册和版本管理；
- 新增 `server/aestheticReview.ts`：确定性计划与画面风险复核；
- `server/route.ts`：编排上下文、导演、搜索、编译和复核；
- `server/validate.ts`：把内部计划编译成现有 `RouteDecision`，保留参数钳制和名称校验；
- `server/memory.ts`：在内部摘要约定中增加审美轨迹字段的整理提示；
- `server/searchMcp.ts`、`server/searchMcpClient.ts`、`server/webSearch.ts`：继续作为
  外部资料 provider；
- `shared/protocol.ts`：只保留前端需要的公开决策；内部计划类型留在服务端；
- `src/app/useGeneration.ts`：继续作为唯一执行入口，不在组件层重复判断能力；
- `src/core/aiPresets.ts`：作为生成式能力的结构化模板来源，不扩成任意提示词集合。

若实现时需要新增目录或公开类型，只增加与本设计直接相关的文件，不顺手重构相邻页面。

## 10. 验收

### 10.1 行为验收

| 场景 | 应有结果 |
| --- | --- |
| “把脸提亮一点，背景别抢” | 本地调整脸部和背景关系，不生成，回复说明保留项 |
| “天空再蓝一点” | 只做色彩关系，不替换天空 |
| “后面那个人去掉，再整体亮一点” | 一次生成去人，本地轻提亮；不重复做同一件事 |
| “做得像电影一点” | 先走本地色彩、对比和质感；不重画场景 |
| “这张拍得好丑” | 指出真实画面优点，给一个低风险下一步，不空夸、不读心 |
| “不知道该怎么修” | 两条清楚方向，各说明效果和代价，推荐更稳的一条，不擅自生成 |
| “随便帮我修一下” | 用户已授权，可执行一套克制的本地方向，并保留可回退 |
| “最近某相机发布了吗” | 必要时搜索公开资料并附来源；照片修改照常可用 |
| 搜索不可用 | 不暴露失败，不编事实，按照片和会话正常处理 |
| 历史提供的是旧偏好，用户本轮说“这次冷一点” | 以本轮为准，历史只作背景 |
| 模型输出新能力名或越界参数 | 丢弃或钳制，不调用未注册能力 |
| 模型试图用生成代替本地磨皮 | 复核拦截生成，只保留本地人像调整 |

### 10.2 自动化验收

- `server/validate.test.ts`：计划编译、参数合并、重复动作、无效能力、名称白名单和回退；
- `server/aestheticReview.test.ts`：过度磨皮、重复调色、错误生成、身份保留和事实边界；
- `server/prompt.test.ts`：身份、场景 Skill、能力目录和内部词约束；
- `server/route.test.ts`：本地 / 生成 / 咨询 / 搜索 / 记忆 / 失败组合；
- `server/memory.test.ts`：审美轨迹摘要、旧偏好冲突和隐私边界；
- `src/app/useGeneration.test.ts`：编译后的计划仍只通过现有执行入口落地；
- 真实模型抽样只手动运行，覆盖金色样例；自动测试使用固定模型输出，不产生费用；
- 浏览器验收使用桌面 Chromium，确认正常回复、来源链接、失败回退和控制台无错误；
- 本任务不修改手机布局，不运行或宣称完成手机视觉验收。

### 10.3 审美质量检查

建立一组固定测试照片和失败照片，至少覆盖人像、逆光旅行、夜景、产品、食物、建筑和旧照。
每条样例同时检查：

- 技术完整性：无明显过曝、死黑、脏色、断层或异常锐化；
- 主体关系：第一眼落点清楚，背景不压过主体；
- 色彩关系：肤色、产品色和现场光可信，风格服务内容；
- 真实质感：人物身份、皮肤、材质和边缘没有被生成感破坏；
- 克制程度：一项关键动作加少量补充，不出现“所有效果都来一点”；
- 回复质量：有画面依据、有判断、有下一步，不套固定话术或暴露内部流程。

审美验收以成片对比和人工盲评为准，不用“参数看起来合理”代替真实画面结果。

## 11. 实施顺序

1. 建立主审美规则、能力注册表和内部计划类型；
2. 把现有 `route` 决策编译进新的导演计划，保证现有调色、预设、Lut、生成、搜索和记忆
   行为不退化；
3. 加入确定性复核和回复守卫；
4. 加入开放咨询、情绪接住和双方向思路；
5. 用固定照片集完成质量验收和桌面浏览器验收；
6. 通过全部测试、类型检查和构建后，再接入新的声明式场景能力。

在规格由用户确认之前，不进入实现计划，也不修改功能代码。
